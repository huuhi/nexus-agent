## 0. 开始前：五件必须先知道的事

| # | 事项 | 结论 |
|---|---|---|
| 1 | 后端地址 | `http://localhost:8080`，**没有 `context-path`**，所有接口以 `/api/...` 开头 |
| 2 | 鉴权头 | **`token: <JWT>`** ❗不是 `Authorization: Bearer`，这是本项目最容易写错的一处 |
| 3 | SSE | **不能用浏览器原生 `EventSource`** —— 它不支持自定义请求头，带不上 `token`。必须 `fetch` + `ReadableStream` 自己解析 |
| 4 | CORS | 后端**已经配好了**，dev 默认放行 `http://localhost:5173`；**prod 默认关闭**。换端口/换域名要改 `nexus.agent.cors.allowed-origins`（见 §1.2） |
| 5 | 统一响应 | 一律 `{code, msg, data, total}`。**HTTP 200 + `code=1` 也是失败**，判断成败看 `code` 不看状态码 |

如果这五条里有任何一条你没照做，后面的联调一定卡住且看不出原因。

## 1. 环境与联调准备

### 1.1 端口与路径

后端没有配 `server.port`（`application.yml` 里只有 `server.shutdown`），所以是 Spring Boot 默认 **8080**。
没有 `context-path`，接口前缀就是 controller 上的 `@RequestMapping`：

```
/api/user/...       用户、登录、设置、记忆、配额
/api/chat/...       对话（SSE）与模型列表
/api/history/...    会话列表与历史消息
/api/artifact/...   本会话 AI 产出的文件
/api/file/...       文件上传与列表
# ★ 2026-10-04 本地知识库已下线，/api/knowledge/* 与 enableRag 均不再存在（知识库检索改用乐享，见 docs/乐享知识库接入（前端）.md）
/api/mcp/...        MCP 服务配置
/api/common/...     邮箱验证码
```

### 1.2 跨域（CORS）：后端已经配好了

后端**有**跨域配置（`nexus-agent-service/.../config/CorsConfig.java`），
走的是 `CorsFilter`（Servlet 过滤器），并且**默认已经放行前端调试端口**：

```yaml
# application.yml（dev 默认）
nexus:
  agent:
    cors:
      enabled: true
      allowed-origins: http://localhost:5173,http://127.0.0.1:5173
```

所以用 Vite 默认端口 5173 直连 `http://localhost:8080` 就能通，
**不需要**额外配代理。换端口只要改上面这一行（支持 `http://localhost:*` 这种通配写法）。

> 📌 之前这里写成"后端没配 CORS"是**错的** —— 那份判断只 grep 了
> `addCorsMappings` / `@CrossOrigin` / `allowedOrigin`，漏掉了走 `CorsFilter` 的写法。
> 实际排查跨域请直接 grep **`cors`（不区分大小写）**。
> 顺带说明：老版本是 `allowedOriginPatterns("*")` + `allowCredentials(true)`，
> 等于对**任意网站**开放，已在本次修复为「配置驱动 + prod 默认关」。

三个要点：

1. **放行的是 `token` 头**（`Access-Control-Allow-Headers: token, Content-Type`）。
   本项目鉴权靠它，不放行的话预检就失败、请求根本发不出去。
2. **预检（OPTIONS）由 `CorsFilter` 直接短路**，不会走到登录拦截器 —— 所以不存在
   "预检被 401" 的问题。这也是选 `CorsFilter` 而不是 `WebMvcConfigurer#addCorsMappings` 的原因。
3. **prod 默认关闭**（`application-prod.yml` 里 `enabled: false`）。
   上线时二选一：同源部署（见下方方案 B，不用开 CORS），
   或跨域部署时把 `enabled` 改成 `true` 并填**精确域名**（别填 `*`）。

如果你的 Vite 端口不是 5173，两种改法：

**方案 A：改后端配置（最直接）**

```yaml
nexus:
  agent:
    cors:
      enabled: true
      allowed-origins: http://localhost:5173,http://localhost:3000
```

**方案 B：同源部署（生产推荐，连 CORS 都不用开）**

用 Nginx 把前端静态资源和后端挂在同一域名下：

```nginx
server {
    listen 80;
    root /usr/share/nginx/html;      # 前端 build 产物
    try_files $uri $uri/ /index.html;

    location /api/ {
        proxy_pass http://app:8080;
        proxy_http_version 1.1;
        proxy_set_header Connection '';   # SSE 关键：禁用 chunked 缓冲
        proxy_buffering off;
        proxy_read_timeout 3600s;         # 长对话别被 60s 掐断
    }
}
```

> ⚠️ 若你仍用 Vite 代理（`/api` → `8080`），注意某些 http-proxy 版本**会缓冲 SSE**。
> 判据：`message` 事件不是逐步到达，而是 `finish` 之前一整块涌出来。
> 这时改成直连 8080（走上面的 CORS）即可。

## 2. 认证与登录

### 2.1 三种方式

`LoginType` 只有两个值：**`CODE`**（邮箱验证码）和 **`PASSWORD`**（密码）。

| 场景 | 接口 | 前置 |
|---|---|---|
| 验证码登录 / 未注册自动注册 | `POST /api/user/login`，`type: "CODE"` | 先 `POST /api/common/email?email=xxx` |
| 密码登录 | `POST /api/user/login`，`type: "PASSWORD"` | 用户已设过密码 |
| 注册（其实验证码登录会自动注册） | `POST /api/user/register` | 同上 |
| 忘记密码 / 首次设密码 | `PUT /api/user/password` | 同上 |

### 2.2 完整时序（验证码登录）

```
用户输入邮箱
   │
   ├─► POST /api/common/email?email=a@b.com        →  {code:0, data:"验证码发送成功！"}
   │      （前端开始 60s 倒计时，按钮置灰）
   │
用户输入验证码
   │
   └─► POST /api/user/login  {email, code, type:"CODE"}
          →  {code:0, data:"eyJhbGciOi..."}       ← data 就是 JWT 字符串
             存起来 → 跳首页
```

### 2.3 token 存哪、怎么带

- 存 **`localStorage`**（本项目没有 refresh token，JWT 过期就只能重新登录）。
  用 `sessionStorage` 也行，但刷新标签页会丢。
- **每个请求都要带 `token` 头**。用 axios 请求拦截器统一注入，不要在每处手寫：

```ts
// src/api/http.ts
const http = axios.create({ baseURL: '/', timeout: 0 });   // SSE 请求要 timeout: 0

http.interceptors.request.use((cfg) => {
  const token = localStorage.getItem('token');
  if (token) cfg.headers.token = token;        // ❗键名就是 token，不是 Authorization
  return cfg;
});
```

### 2.4 401 的统一处理

未登录 / token 过期 / 签名不符时，`LoginCheckInterceptor` 直接短路：

```
HTTP/1.1 401
Content-Type: application/json;charset=UTF-8

{"code":1,"msg":"NOT_LOGIN","data":null,"total":null}
```

> 📌 注意：`docs/sse-contract.md` 里曾写成"401 + 纯文本 `NOT_LOGIN`"，
> 实际代码写的是 JSON（`JSONUtil.toJsonStr(Result.error(msg))`），已同步修正。

响应拦截器里统一处理：

```ts
http.interceptors.response.use(
  (res) => res,
  (err) => {
    if (err.response?.status === 401 || err.response?.data?.msg === 'NOT_LOGIN') {
      localStorage.removeItem('token');
      router.push('/login');
      return Promise.reject(new Error('登录已失效，请重新登录'));
    }
    return Promise.reject(err);
  }
);
```

### 2.5 免鉴权接口（只有这 4 + 文档路径）

```
POST /api/user/login
POST /api/user/register
PUT  /api/user/password
POST /api/common/email
/swagger-ui.html、/swagger-ui/**、/v3/api-docs、/v3/api-docs/**   （P3-4）
/actuator/health、/actuator/health/**、/actuator/info              （P3-3，容器探针）
```

**除了这些，所有 `/api/**` 都必须带 `token`。**

## 3. 统一响应结构与错误约定

### 3.1 `Result` 四个字段

```jsonc
{
  "code": 0,        // 0 = 成功；1 = 业务失败
  "msg":  "ok",     // 成功时是 "ok"，失败时是**可直接展示给用户的中文提示**
  "data": { ... },  // 成功时的载荷；无返回值时为 null
  "total": null     // 本项目所有接口都没做分页，恒为 null，别用它
}
```

失败示例：

```jsonc
{ "code": 1, "msg": "邮箱格式错误！", "data": null, "total": null }
```

### 3.2 前端封装建议

```ts
export async function request<T>(cfg: AxiosRequestConfig): Promise<T> {
  const res = await http.request(cfg);
  const body = res.data as Result<T>;
  if (body.code !== 0) {
    // 后端 msg 已经是人话，直接提示即可，不要自己再翻译一遍
    ElMessage.error(body.msg || '操作失败');
    throw new Error(body.msg);
  }
  return body.data as T;
}
```

### 3.3 错误文案从哪来

后端 `GlobalExceptionHandler` 的规则：

| 情况 | HTTP | 返回 |
|---|---|---|
| 业务异常（`NotSupport` / `PermissionDenied` / `NotFound` / `Unauthorized` / `QuotaExceeded`） | **200** | `code=1` + 具体中文提示 |
| 参数校验失败（`@Valid`） | **200** | `code=1` + 字段上的 `message`（如"邮箱不能为空！"） |
| 未预期异常 | **500** | `code=1` + "系统内部错误，请稍后重试或联系管理员"，**不含堆栈** |
| Spring 标准异常（404 / 405 / 415） | 原状态码 | `code=1` + 状态短语 |

**结论**：前端只需要一个 `if (code !== 0) 显示 msg` 的分支，不用再维护错误码表。

**唯一的例外**：配额超限（`QuotaExceededException`）的文案比较长，
建议在设置页做专门展示（"您的 token 配额已用完（已用 X / 上限 Y）…或等待下一周期重置（当前周期：MONTHLY）"），
弹 toast 会截断。

## 5. 接口详解

### 5.1 登录 / 注册 / 密码 / 验证码

**`POST /api/common/email`**（免鉴权）

```http
POST /api/common/email?email=a@b.com
```
```jsonc
{ "code": 0, "msg": "ok", "data": "验证码发送成功！", "total": null }
```

**`POST /api/user/login`**（免鉴权）

```jsonc
// 请求体 UserLoginDTO
{ "email": "a@b.com", "password": "", "code": "123456", "type": "CODE" }
// type: "CODE" | "PASSWORD"
// 验证码登录时 password 可省略；密码登录时 code 可省略
```
```jsonc
// 响应：data 就是 JWT 字符串
{ "code": 0, "msg": "ok", "data": "eyJhbGciOiJIUzI1NiJ9...", "total": null }
```

**`POST /api/user/register`**（免鉴权）

```jsonc
// UserRegisterDTO
{ "email": "a@b.com", "username": "张三", "code": "123456" }
// → data 同样是 JWT
```

**`PUT /api/user/password`**（免鉴权）

```jsonc
// UserPasswordDTO —— 三个字段都必填
{ "email": "a@b.com", "code": "123456", "password": "xxxxxx" }
```

> ⚠️ 后端校验失败会返回 `{"code":1,"msg":"邮箱格式错误！"}` 之类的中文，
> 直接展示即可。前端的正则校验只用来做**即时反馈**，不要替代后端校验。

### 5.2 会话列表与历史消息

**`GET /api/history`** —— 侧栏数据来源

```jsonc
{
  "code": 0,
  "data": [
    {
      "sessionId": "8f2c1a...",
      "userId": 1,
      "title": "帮我写一份季度报告",
      "createTime": "2026-10-01T09:12:33.000+00:00",
      "updateTime": "2026-10-01T09:40:02.000+00:00"
    }
  ]
}
```

**前端要注意的**：

- 列表**没有分页**，用户聊多了会很长 —— 首版可以只取前 N 条 + 前端按天分组（今天 / 昨天 / 更早）。
- `title` 可能为 `null`（后端没生成标题时）→ 回退成"新对话"或取首条用户消息的前 20 字。
- 排序：**以后端返回顺序为准**（按 `updateTime` 倒序），前端别再自己排一次，容易和后端不一致。

**`GET /api/history/{sessionId}`** —— 点开某个会话时加载

返回 `List<MessageVO>`，单个元素结构：

```jsonc
{
  "type": "AI",                 // USER | AI | THINK | CONTENT | TOOL_EXECUTION
                                // | TOOL_EXECUTION_RESULT | ERROR | ARTIFACT | CUSTOM
  "content": "你好，有什么可以帮你？",
  "thinking": null,             // 思考过程（type=THINK 时有值）
  "attachedFiles": [            // 用户随消息带的附件（可空）
    { "id": "12", "fileName": "数据.xlsx", "fileUrl": "https://...", "fileSize": 1024, "extension": "xlsx" }
  ],
  "toolResultVO": null,         // { id, toolName, result, isError }
  "toolRequestList": null,      // [ { id, toolName, arguments } ]
  "artifact": null              // { id, name, url, size, extension, sourcePath }
}
```

> 📌 **历史里的 `type` 和 SSE 里的 `type` 不是一回事**：
> 历史消息用 `MessageType`（**全大写**，如 `AI` / `TOOL_EXECUTION`）；
> SSE 事件名用 `SseEventType`（**全小写**，如 `tool_execution`）。
> 这是历史遗留，别写反 —— 具体见 §6.2。

**`DELETE /api/history?sessionId=xxx`**

删除后前端要把该会话从侧栏移除；如果当前正打开它，跳到新对话页。

**`PUT /api/history/{sessionId}/title`** —— 会话重命名

```http
PUT /api/history/8f2c1a.../title
token: <登录令牌>
Content-Type: application/json

{ "title": "季度报告 v2" }
```

- 成功：`{"code":0,"msg":"ok","data":null}`。
- `title` 会被 `trim`，最长 100 字符，空串会被拒。
- **改完不要在本地直接改侧栏文案就完事**：后端同时把 `updateTime` 刷成当前时间，
  列表顺序会变 —— 保存成功后重新 `GET /api/history` 拉一次最省心。
- 失败码（HTTP 200 + `code=1`，见 §3）：
  - `会话 ID 格式不正确` —— `sessionId` 不是合法 UUID（多半是路由拼错了）；
  - `标题不能为空` / `标题不能超过 100 个字符`；
  - `会话不存在或不属于当前用户` —— 会话被删了，或者在改别人的会话（越权写已被拦）。

**`GET /api/history/search?keyword=xxx`** —— 搜索框

```jsonc
{
  "code": 0,
  "data": [
    {
      "sessionId": "8f2c1a...",
      "title": "帮我写一份季度报告",
      "updateTime": "2026-10-01T09:40:02.000+00:00",
      "matchType": "CONTENT",       // TITLE = 标题命中，CONTENT = 消息正文命中
      "snippet": "…第三季度的**营收**同比增长 12%…",
      "hitCount": 2                  // 该会话里命中的消息条数（标题命中时为 0）
    }
  ]
}
```

**前端要注意的**：

- 结果是**会话粒度**，一个会话只出现一次；`matchType=TITLE` 的整体排在 `CONTENT` 前面。
- `snippet` 只在 `matchType=CONTENT` 时有值（标题命中的话标题本身就是命中内容）；
  需要**高亮关键词**时用 `keyword` 在 `snippet` 里做一次不区分大小写的替换即可，
  片段两端的 `…` 表示被截断了。
- `title` 可能为 `null`（该会话还没生成标题）→ 回退成"新对话"。
- 关键词为空或超过 100 字符会被拒（`code=1`），所以**前端要做防抖 + 非空判断**，
  别在输入框刚清空时就发请求。
- 后端不分页，最多返回 30 个会话；搜索是**全量匹配**（不是增量），每次输入都重新查。

### 5.5 文件与知识库

**上传图片**：

```http

Content-Type: multipart/form-data
字段名: file
→ data: "https://oss.../xxx.png"      （字符串 URL）
```

**批量上传文件**：

```http
POST /api/file
Content-Type: multipart/form-data
字段名: files（可多个）, bizType（KNOWLEDGE | CHAT | ARTIFACT）
→ data: [ KnowledgeFileVO ]
```

`KnowledgeFileVO`：`{id, fileUrl, fileName, fileSize, failReason, uploadStatus, createTime, bizType, extension}`

**知识库四步走**：

```http
POST /api/knowledge          {name, describe?, isPublic?, languageCode?}   → 创建
```

⚠️ `KnowledgeFileDTO` 的 `configId` / `model` **已废弃**（向量模型固定用系统模型），
前端不要传、也不要展示这两个字段。

### 5.6 MCP

```http
GET    /api/mcp/service   → 服务商预置模板 [McpServerItemVO]
GET    /api/mcp           → 我已配置的     [McpServerItemVO]
GET    /api/mcp/{id}      → McpDetailVO（多了 header 字段）
POST   /api/mcp           → 请求体是**数组** [McpServerItemDTO]
PUT    /api/mcp           → 单个 McpServerItemDTO
DELETE /api/mcp/{id}
```

`McpServerItemVO`：`{strId, id, url, description, name, logoUrl, type, available}`
`McpServerItemDTO`（提交时用）：`{id?, strId, url, description, name, logoUrl, type, header?, available?}`

> `id` 在 VO 里是 **String**，在 DTO 里是 **Long** —— 提交时记得 `Number(strId)` 转换，别直接回传字符串。

> ⚠️ **`header` 可以整个不传**（2026-10-04 修复）。
> 从「服务商预置列表」一键添加时，`McpServerItemVO` **不含 header**（凭据不该出现在列表接口），
> 所以 `POST /api/mcp` 的元素大概率没有这个字段 —— 后端会存成 `{}`。
> 只有用户自己在「编辑」里填了鉴权头，才需要带上：
> `{..., "header": {"Authorization": "Bearer xxx"}}`。
>
> **header 的三条硬约束**（后端会拦，返 400 而不是 500）：
> 1. 头的**值必须是字符串** —— 数字/对象/数组会被拒（`{"X-Count": 123}` 不行，要写 `"123"`）
> 2. 头的**值不能含换行 / NUL** —— 那是请求头注入
> 3. 头的**名字必须符合 HTTP token 规范** —— 不能有空格、冒号、中文
>
> `GET /api/mcp/{id}` 返回的 `header` 是**已解析好的对象**（不是 JSON 字符串），
> 前端可以直接 `Object.entries(detail.header)` 渲染成输入框，不用自己 `JSON.parse`。

## 6. SSE 流式对话：前端视角完整说明

权威契约在 [`docs/sse-contract.md`](./sse-contract.md)，这一节是把其中最关键的部分
用前端的话重讲一遍，并补上状态机和代码。

### 6.1 为什么不能用 `EventSource`

`new EventSource(url)` **不能自定义请求头**，而本项目鉴权靠 `token` 头 → 带不上 → 401。
而且它是 GET，本项目是 POST + JSON body。

所以用 `fetch` + `ReadableStream`（或 `@microsoft/fetch-event-source`）。

### 6.2 七种事件与时序

```
请求发出
  │
  ▼
run                     ← 第一帧，必收。拿到 runId 与 sessionId
  │
  ├─ message (THINK)    ← 思考过程，多次
  ├─ message (CONTENT)  ← 正文，多次
  ├─ tool_execution     ← 工具调用请求（arguments 是**流式片段**）
  ├─ tool_execution_result
  ├─ artifact           ← AI 交付的文件
  │
  ▼
finish  |  error
```

每帧都是同一信封：

```jsonc
{ "seq": 7, "runId": "a1b2c3", "event": "tool_execution", "data": { ... } }
```

| `event` | 载荷 `data` |
|---|---|
| `run` | `{sessionId, isNewSession}` |
| `message` | `{type:"THINK"\|"CONTENT", thinking?, content?}` |
| `tool_execution` | `{type:"TOOL_EXECUTION", toolRequestList:[{id,toolName,arguments}]}` |
| `tool_execution_result` | `{type:"TOOL_EXECUTION_RESULT", toolResultVO:{id,toolName,result,isError}}` |
| `artifact` | `{type:"ARTIFACT", artifact:{id,name,url,size,extension,sourcePath}}` |
| `finish` | `{status:"DONE"}` |
| `error` | `{type:"ERROR", message, hint}` |

> ⚠️ **事件名全小写**（`tool_execution`），而 **消息体里的 `type` 是大写**（`TOOL_EXECUTION`）。
> 两套命名并存是历史原因，别混用。

### 6.3 推荐的消息状态机

给每条 AI 回复维护一个状态：

```
idle ──用户点发送──► pending（等首帧 run，此时显示"思考中…"）
                      │ 收到 run → 记下 sessionId / runId
                      ▼
                   streaming（逐帧 append）
                      ├──► finish      → done
                      ├──► error       → error（展示 message + hint，保留已到的正文）
                      └──► 用户点停止  → interrupted（保留已到的正文，标"已停止"）
```

**关键**：`error` 和 `interrupted` 都要**保留已经收到的正文** ——
后端在出错前会先把已生成的正文冲刷出来，那些内容是有效的，别丢。

### 6.4 六个必踩的坑（逐条给对策）

**① 正文是"批量增量"，必须 append 不能替换**

后端攒够 200 字符或 60ms 才推一帧，一帧可能含多个 token。

```ts
// ✅ 对
buffer.content += chunk.content;
// ❌ 错：会只剩最后一帧
state.content = chunk.content;
```

**② 思考与正文分开累积**

`type` 是 `THINK` 还是 `CONTENT` 决定往哪个字符串累加，别拼一起。
UI 上建议把 THINK 放进可折叠的"思考过程"区块（默认收起）。

**③ 工具参数是流式片段，按 `id` 累积**

`tool_execution` 的 `arguments` 会被拆成多帧（`{"cmd":` → `{"cmd":"ls` → …），
早期帧是**非法 JSON**。

```ts
const argsBuf = new Map<string, string>();
// 每帧：argsBuf.set(id, (argsBuf.get(id) ?? '') + argsChunk)
// 只在**展示时**尝试 JSON.parse，失败就原样显示字符串（带 try/catch）
```

**④ Markdown 不要边流边渲染**

流式过程中反复渲染 Markdown 会造成持续重排，页面会卡（这正是之前"输出字符很不流畅、卡卡的"的根因之一）。
做法：**流式中按纯文本 append**（可以先做极轻量的换行保留），
收到 `finish` 后**整体渲染一次 Markdown**。

**⑤ 用 `requestAnimationFrame` 批量提交 DOM 更新**

不要每个事件都 `setState`。把帧塞进缓冲，`rAF` 里统一 flush：

```ts
let pending = false;
function scheduleFlush() {
  if (pending) return;
  pending = true;
  requestAnimationFrame(() => { pending = false; render(); });
}
```

**⑥ 自动滚动要节流，且用户上滚时停**

只在"用户贴着底部"时才自动滚；用户手动上滚后停止自动滚动，并显示"回到最新"按钮。

### 6.5 中断 / 断线 / 恢复

- **中断（用户点停止）**：`AbortController.abort()` 即可。前端标记 `interrupted`。
  后端会感知连接断开并停止生成（不会产生额外费用）。
- **丢帧检测**：`seq` 从 1 单调递增，出现跳号说明中间断了。
- **断线恢复**：**服务端没有实现回放**（诚实说明，见 `sse-contract.md §5`）。
  正确做法是用 `sessionId` 重新 `GET /api/history/{sessionId}` 拉历史，
  恢复已完成的消息，并提示用户重发最后一条。
- **报错定位**：`error` 事件带 `runId`，让用户把它复制给开发者，
  后端可直接 `grep "RUN runId=<值>"` 拿到完整现场。

## 8. 设计系统：极简黑白

### 8.1 参考对象与它们的共同点

对齐 **ChatGPT / Claude / DeepSeek / Kimi** 的共性（这些是已被验证的共识，不是个人审美）：

1. **几乎无彩色**：只有黑、白、灰。彩色只用于语义（错误红、成功绿）和品牌标识。
2. **信息密度低**：大量留白，一屏只做一件事。
3. **正文优先**：正文字号 15–16px、行高 1.7，是页面上最"重"的元素。
4. **边框代替阴影**：分隔靠 1px 细线，不用卡片阴影堆叠。
5. **只有一个强调色**：主按钮是黑底白字（light）/ 白底黑字（dark）。

### 8.5 关键组件规范

**输入框**
- 自增高，`min-height: 52px`，`max-height: 200px`（超过就内部滚动）
- 底部右侧放发送按钮：圆形，40×40，`--accent` 底 + `--accent-fg` 图标
- 生成中时发送按钮变成**停止按钮**（方形图标），这是所有 AI 站的统一做法
- 上方一排轻量的功能入口：模型选择、`enableLexiangRag` 开关、附件 —— 都用图标 + Tooltip，不要文字标签堆一排

**消息**
- AI 消息：左侧 28px 圆形头像（或方形 logo），右侧内容区，**无背景色**
- 用户消息：**可选**极浅的 `--bg-subtle` 圆角块，或者同样左对齐 + 头像区分（推荐后者，更简约）
- 消息下方 hover 才出现操作条：复制 / 重新生成 / 删除（默认隐藏，避免视觉噪音）

**"思考过程"区块**
- 默认**收起**，标题"已思考"，点击展开
- 文字用 `--text-muted`、14px、左侧 2px 竖线，和正文明确区分

**工具调用卡片**
- 折叠展示：`工具名 · 执行中… / 已完成 / 失败`
- 展开后显示参数（JSON，格式化）和结果
- 失败（`isError=true`）时才允许出现红色，且只用 `--danger` 做文字色 + 1px 左边框，不要整个卡片变红

**产物（下载卡片）**
- 一行式：`[文件类型图标] 报告.docx  12.1 KB  [下载]`
- 12px 圆角 + 1px 边框 + 无阴影

**侧栏**
- 宽 260px，背景 `--bg-subtle`，右侧 1px 边框
- 会话项高度 36px，字号 14px，选中态背景 `--bg-hover` + 左侧 2px `--text` 竖线
- hover 右侧出现"更多"图标（重命名 / 删除）

### 8.6 动效原则（克制）

- 时长：hover / 颜色过渡 **150ms**；展开折叠 **200ms**；弹层 **200ms**
- 缓动：`cubic-bezier(.2, .8, .2, 1)`（ease-out 感）
- 只允许动 `opacity` 和 `transform`，不要动 `width` / `height` / `top`
- **流式文本不加打字机动画**（后端已经是流式推的了，再加动画只会更卡）
- 唯一的"仪式感"动效：生成中在头像旁放一个 3 点呼吸或 1px 进度条，静态即可

### 8.7 无障碍底线

- 所有可点元素有可见的 focus ring：`outline: 2px solid var(--text); outline-offset: 2px`
- 图标按钮必须有 `aria-label`
- 深色模式跟随 `prefers-color-scheme`，并允许手动切换（存 localStorage）
- 键盘：`Enter` 发送、`Shift+Enter` 换行、`Esc` 停止生成（这个很讨喜）

## 9. 一条完整链路的联调顺序（照着做完就跑通了）

```
1. 起后端（8080）+ 配好 Vite proxy（§1.2）
   └ 验证：浏览器开 http://localhost:8080/swagger-ui.html 能出页面

2. 登录页
   POST /api/common/email → 收邮件拿验证码
   POST /api/user/login（type=CODE）→ 拿到 JWT
   └ 验证：localStorage 里有 token；axios 拦截器确实带上了 token 头

3. 会话侧栏
   GET /api/history → 空数组也正常（新用户）
   └ 验证：Network 面板里请求头有 token，返回 code=0

4. 新对话（最关键）
   POST /api/chat/stream（sessionId=null）
   └ 验证 4 件事：
      · 收到 run 事件 → 拿到 sessionId，把 URL 换成 /chat/<sessionId>
      · 正文是逐步 append 的（不是一次性涌出）
      · 点停止能中断
      · finish 后整段渲染 Markdown / 代码高亮正常

5. 刷新页面
   GET /api/history/{sessionId} → 历史能还原
   └ 验证：上一步的对话在刷新后还在

6. 侧栏刷新
   GET /api/history → 出现刚才那条会话

7. 重命名 + 搜索
   PUT /api/history/{sessionId}/title → 重新拉 GET /api/history 看标题和排序都变了
   GET /api/history/search?keyword=<刚才聊过的一个词>
   └ 验证：能搜到刚那条会话；matchType=CONTENT 时 snippet 里能看到关键词
   └ 验证：keyword 传空 → 返回 code=1（前端要拦住不发请求）

8. 错误处理
   手动把 localStorage 的 token 改成乱的 → 应该被踢回登录页（401）
```
