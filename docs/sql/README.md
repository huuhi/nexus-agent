# docs/sql — 数据库变更管理

## 为什么有这个目录

项目**没有引入 Flyway / Liquibase**，schema 完全靠手工执行 SQL。
结果就是：新环境搭不起来、各环境表结构悄悄漂移、改表没有记录可查。

本目录是**过渡方案**：在正式引入迁移工具（见 `重构计划.md` P3）之前，
所有表结构变更必须以可重放的 SQL 文件形式落在这里，并按序号命名。

### 命名与维护约定

1. **只增不改。** 已执行过的文件不再修改内容；需要调整就新建下一个序号。
   唯一例外是 `001_baseline.sql` 本身写错了（字段类型/约束有误）——那属于修 bug，需在提交信息里说明。
2. **必须可重放。** 增量文件用 `if not exists` 等幂等形式。
3. **文件顶部写清**：目的、影响表、是否可回滚；破坏性变更附回滚 SQL。
4. **实体与 SQL 必须同步改**（`nexus-agent-domain` ↔ 本目录），不能只改一边。

### 复核查询（换环境重建后建议再跑一遍）

```sql
-- 1) 表清单，应为 12 张
select table_name from information_schema.tables
where table_schema='public' and table_type='BASE TABLE' order by 1;

-- 2) 主键，应为 12 条
select c.relname as tbl, con.conname
from pg_constraint con join pg_class c on c.oid = con.conrelid
join pg_namespace n on n.oid = c.relnamespace
where n.nspname='public' and con.contype='p' order by 1;

-- 3) 外键，应为 4 条
select con.conname from pg_constraint con
join pg_class c on c.oid = con.conrelid
join pg_namespace n on n.oid = c.relnamespace
where n.nspname='public' and con.contype='f' order by 1;

-- 4) 索引，应含 9 个业务索引 + 各主键/唯一约束自带的索引
select indexname from pg_indexes where schemaname='public' order by 1;

-- 5) 向量列维度，应为 1024
select attname, format_type(atttypid, atttypmod) as type
from pg_attribute where attrelid='public.knowledge_embedding'::regclass
  and attname='embedding';

-- 6) 配额周期两列，应返回 2 行（没跑 007 会是 0 行 → 登录会 500）
select column_name from information_schema.columns
where table_schema='public' and table_name='users'
  and column_name in ('token_period','token_period_start');
```

## 这份基线是怎么来的（重要）

它**不是**从旧库照抄的，而是**重新设计**的。原因：

开发库曾被自动程序清空过，灾后重建出来的结构是不完整的：

- 12 张表**全部没有主键、唯一约束、外键，也没有任何索引**
- `sys_file` 表**不存在**（文件上传会在运行期报 `relation "sys_file" does not exist`）
- `knowledge_base_file` **缺 `file_name` 列**（知识库入库与详情查询都会报错）

旧数据已确认可全部舍弃（仅测试账号），因此改为按「**代码实际需要什么**」重新设计。
设计依据是三个来源逐项交叉推导，而不是凭经验猜：

1. `nexus-agent-domain` 的实体（`@TableName` / `@TableId` / `@TableField`）
2. `nexus-agent-mapper` 的 XML（resultMap 映射的列、自定义 SQL 引用的列）
3. Service 层真实出现的 SQL 与查询条件（决定索引）

## 设计要点与理由

| 设计 | 理由 |
|---|---|
| 所有 id 列用 `bigint GENERATED BY **DEFAULT** AS IDENTITY` | 各实体的 `@TableId` 多为默认 `ASSIGN_ID`（应用生成雪花 ID），而 `ChatMemoryMapper.xml` 的自定义 `insertBatch` 又**不带 id**、依赖数据库生成。`BY DEFAULT` 同时接受显式和自增两种方式；用 `ALWAYS` 则应用传 ID 时会报错 |
| `users.email` 加 **UNIQUE** | 登录/注册全部以 email 为依据（`UserServiceImpl` 用 `query().eq("email",...).one()`），而 MP 的 `.one()` 命中多行会抛异常。**这是硬需求，不是可选项** |
| 删除 `user_config.user_default` | 库里有该列，但 `UserConfig` 实体无对应字段，代码从不读写 |
| `user_config.mcp_token` → `varchar(512)` | `Encryptors.text` 输出十六进制，长度 = (16字节IV + 明文) × 2。ModelScope token 超过 48 字符时 `char(128)` 就会溢出报错 |
| `user_memory.source` → `varchar(64)` | `MemoryTool.saveLongMemory` 会把**会话 ID（UUID，36 字符）**写进 `source`，原 `char(32)` 装不下，插入报 `value too long` |
| `sys_file.fail_reason` → `varchar(500)` | `FileServiceImpl` 失败时写入 `substring(msg, 0, 450)`，必须 ≥450 |
| `knowledge_embedding.embedding` → `vector(1024)` | 原库是**无维度**的 `vector`，而 pgvector **无法在无维度列上建索引** → RAG 检索是全表扫描。同时无维度时换错向量模型不会被拦住 |
| 新增 HNSW 向量索引 | `PgVectorEmbeddingStore` 用余弦距离（`<=>`）检索，配 `vector_cosine_ops` |
| 9 个普通索引 | 每一条都对应代码里真实出现的查询条件（文件内逐条注明了出处），不做无依据的加索引 |
| 只加 4 个外键 | `user_config`、`knowledge_base_file`×2、`skill_mcp_information`。**刻意不给** `chat_memory` / `chat_history_list` / `mcp_information` 加 —— 沿用原作者的设计决定（见 `开发日志.md` 4.20：存在「先插子行、父信息异步补」的写入顺序） |
| 不建 `user_memory.embedding` 列 | 长期记忆当前走 SQL LIKE 检索，向量检索的代码被注释掉了。是否恢复取决于**决策 D4**，定了再加（`重构计划.md` P2-7） |
| 删除 `skill_information`、`user_skill` | 历史死表，代码中已无任何实体或 Mapper 使用（`skill_mcp_information` 的删除走 `002_*.sql`，不回改基线） |

## 从 Navicat 重新导出时的注意事项

如果以后又要用 Navicat 导出，务必先清理再提交：

1. **只导结构，不导数据** —— 原始导出含 267 条真实业务数据（会话内容、加密密钥），
   **绝对不能进 git**
2. **勾选全部表** —— 这次缺失的两张表很可能是导出时没勾全
3. 清理项：
   - 删掉所有 `INSERT INTO` / `COPY` / `SELECT setval`
   - 删掉 pgvector 扩展内部对象（`halfvec`/`sparsevec`/`vector` 三个 TYPE，
     以及 100+ 个 `$libdir/vector` 的 FUNCTION），改用 `CREATE EXTENSION IF NOT EXISTS vector;`
   - 删掉 Navicat 头部里的源库地址等信息
   - 修正顺序为「先 DROP TABLE → 再 DROP SEQUENCE/TYPE」，否则重放会因依赖冲突失败
4. 更推荐：等 P3 引入 Flyway 后用 `pg_dump --schema-only` 生成，格式干净得多
