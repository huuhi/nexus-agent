## 2026-10-06：用户分级配额（NORMAL / TEST / VIP）+ 长期记忆写不进库的修复 + 首字延迟治理

> 配套迁移：**`docs/sql/012_add_user_role_and_file_quota.sql`（需人工执行）**。
> 没执行也能跑：后端三处配额校验都做了「查库失败就降级放行」，不会把接口打挂，
> 但**额度不会生效**，且 `GET /api/user/quota` 会返回 `degraded=true`。

### 1. 唯一需要你改的：`GET /api/user/quota` 多了 4 个字段

响应体在原有字段基础上新增（**老字段一个都没动，是纯增量**）：

```jsonc
{
  "code": 0,
  "data": {
    // ===== 原有字段（不变）=====
    "quota": 1000000,          // token 上限；不限制时为 null
    "used": 12345,
    "remaining": 987655,       // 不限制时为 null
    "unlimited": false,
    "period": "DAILY",         // NONE / DAILY / MONTHLY
    "periodStart": "2026-10-06T00:00:00",
    "degraded": false,

    // ===== 2026-10-06 新增 =====
    "role": "NORMAL",          // 新增：NORMAL / TEST / VIP
    "fileQuota": 100,          // 新增：今日「文件 + 产物」条数上限；不限制时为 null
    "fileUsed": 3,             // 新增：今日已产生条数；统计失败时为 null
    "fileRemaining": 97,       // 新增：不限制时为 null
    "fileUnlimited": false     // 新增：是否不限量
  }
}
```

**可空字段的兜底（必须按这个来，否则会显示错）**

| 字段 | 何时为 `null` | 前端怎么兜底 |
| --- | --- | --- |
| `fileQuota` / `fileRemaining` | 该用户**不限制**文件数量（TEST 档，或运营把 `users.file_quota` 置空） | 显示「不限」，**不要**显示 `0 / 100` 这种假数字 |
| `fileUsed` | 统计 `sys_file` 失败（库异常） | 显示 `--`，**不要**当 0 —— 0 会被读成「今天一个都没用」，与事实可能相反 |
| `role` | 库里还没跑 `012`（该列不存在）时**整个 `data` 会是 `degraded=true` 的占位体** | 见下 |

⚠️ `degraded === true` 时**其余全部字段都不可信**，请统一显示「配额信息暂不可用」，
不要把 `null` 渲染成 `0`。

**展示建议（不是必须）**：设置页或账号区可以显示「今日文件与产物 3 / 100」。
⚠️ 但**判断「还能不能传」不要看 `role`** —— 运营可以单独改某人的 `users.file_quota`，
那时 `role` 是 `NORMAL` 而额度是 200。判断一律看 `fileUnlimited` 与 `fileRemaining`。

### 2. 上传超限：接口会返回 `code=1`（HTTP 仍是 200）

`POST /api/file/upload`（以及其它上传端点）在超出今日额度时：

```jsonc
{
  "code": 1,
  "msg": "今日文件与产物数量已达上限（已用 100 / 上限 100），明天 00:00 自动重置。",
  "data": null
}
```

- **HTTP 状态码是 200**，按 `code !== 0` 判断失败（与全站其它业务失败一致）；
- 直接把 `msg` 弹给用户即可，文案里已带上「已用 / 上限 / 什么时候恢复」；
- 拦截发生在**传到 OSS 之前**，超限不会产生任何存储请求，可以放心让用户重试。

### 3. AI 产物（artifact）超限：没有新事件，前端不用改

`publish_artifact` 在超限时会被后端直接拒绝，**不会**推 `artifact` 事件。
模型会收到结构化失败（`errorCode: QUOTA_EXCEEDED`）并用**普通文字**告诉用户。
所以产物卡片逻辑、SSE 事件契约**一律不变**（见 `docs/sse-contract.md`）。

### 4. 你无感的后端改动（不用改代码，但知道一下排查时有用）

| 改动 | 说明 |
| --- | --- |
| **长期记忆终于能写进库了** | 根因：工具跑在流式回调线程，`UserContextHolder` 恒为 `null` → `user_id` 为 `null` → 撞 `user_memory.user_id NOT NULL`；而写库方法是 `@Async`，异常被吞 → 工具照样返回 `ok`。现在改用 `RunUserRegistry` 反查 userId、去掉 `@Async`、取不到用户就明确报错。 |

| **注册即按角色写额度** | 新用户：`role=NORMAL`、`token_quota=1000000`、`token_period=DAILY`、`file_quota=100`。 |

## 2026-10-05：🔴🔴 文件还是删不掉 —— 真凶是 id 精度丢失（上一轮结论是错的）+ 新增批量删除

### 先纠正上一条

上一条说根因是 `bizType=ARTIFACT` 限制 —— **那个只是次要问题，删掉它不解决问题**。
删掉之后你反馈「还是每次都这样」，是对的。真凶在下面。

### 真凶：19 位雪花 ID 在浏览器里被四舍五入

`sys_file.id` 是雪花 ID，**19 位十进制数**（如 `2107069112529358849`）。
而 JavaScript 的 `number` 是 IEEE754 双精度浮点，能精确表示的整数上限是
`Number.MAX_SAFE_INTEGER = 9007199254740991`，只有 **16 位**。

```jsonc
// 后端返回（修复前）
{ "id": 2107069112529358849 }

// 浏览器 JSON.parse 之后 —— 低位被抹掉
{ "id": 2107069112529358848 }   // ← 差 1，已经不是同一个 id 了
```

实测抽样 4000 个雪花 ID，**99.6% 会被改写**。

删除是「按 id 回传」的操作，链路是
`后端返回 id → 浏览器 double → 前端拼 URL → 后端 WHERE id = ?`，
id 在浏览器里已经变了，**后端必然查不到**，于是每一行都返回
「文件不存在或无权限删除」。

⚠️ **这个坑不只影响删除**：凡是「拿 id 去改 / 删」的接口都会中招
（技能、用户记忆、MCP、聊天记录…）。已在后端统一根治。

### 后端改了什么

**所有 `Long` 字段现在序列化成字符串**（`Integer` 不变）。

```jsonc
// 修复后
{
  "id": "2107069112529358849",     // ← 带引号
  "userId": "7",
  "fileSize": "1048576",           // ← Long，也变字符串
  "code": 0                        // ← Integer，保持数字不变
}
```

| 字段类型 | 之前 | 现在 |
| --- | --- | --- |
| `Long` / `long`（id、userId、**fileSize**、total…） | 数字 | **字符串** |
| `Integer` / `int`（`code`、分页条数…） | 数字 | 数字（**没变**） |

`code` 保持数字很重要 —— `res.code !== 0` 这类判断不能失效。

⚠️ **`fileSize` 也变字符串了**（它是 `Long`）。如果你有按大小排序或格式化的代码：

```diff
- list.sort((a, b) => a.fileSize - b.fileSize)          // 字符串相减 = NaN，排序乱掉
+ list.sort((a, b) => Number(a.fileSize) - Number(b.fileSize))   // 排序时转数字

- formatSize(file.fileSize)                             // 若函数内部做除法，记得 Number()
+ formatSize(Number(file.fileSize))
```

> 为什么不把 `fileSize` 排除掉？因为它**可能**超过 2^53（2PB），只是现实中不会。
> 统一按类型处理，规则简单可靠；真要单独豁免，就得给每个 VO 字段加注解，
> 那正是这次要避免的「治标」做法。**排序/算术时 `Number()` 转一下即可。**

### 🔴 受影响的字段完整清单（不止文件）

除了所有 `id` / `userId`，这些也会变成字符串，**前端如果拿它们做算术会静默出错**：

| 字段 | 出现在 | 典型用法 | 处理|
| --- | --- | --- | --- |
| `fileSize` | `GET /api/file`、`GET /api/artifact`、SSE 产物、历史消息附件 | 排序、大小格式化 | `Number()` |
| `quota` / `used` / `remaining` | `GET /api/user/quota`（`QuotaVO`） | **进度条百分比**、`used / quota` | `Number()` |
| `tokenQuota` / `tokenUsed` | `GET /api/user/config` |同上 | `Number()` |
| `total` | `Result` 包装 | 分页总数 | 一般只显示，不用算 |

```diff
- <Progress percent={used / quota * 100} />          // 字符串相除 = NaN，进度条变空白
+ <Progress percent={Number(used) / Number(quota) * 100} />
```

⚠️ **这类 bug 不会报错**，只会「数字不显示 / 进度条空白 / 排序乱」，
很容易被当成样式问题排查半天。所以请把上面几个字段全仓搜一遍。

### 你要检查的（2 处）

1. **如果代码里有 `Number(id)` / `parseInt(id)` / `+id`，全部删掉。**
   现在 id 已经是精确的字符串，再转数字等于主动把精度搞坏：

   ```diff
   - const id = Number(row.id)
   - const id = parseInt(row.id, 10)
   + const id = row.id            // ← 直接用字符串
   ```

2. **如果代码里有 id 的大小比较或算术，同样不能用。**
   比如 `if (id > 1000)` 换成 `if (String(id).length > 3)`，
   或者干脆改用 `runId` 这类字符串字段做判断。

3. **拼 URL 的地方不用改。** 直接把字符串插进去即可：

   ```js
   axios.delete(`/api/file/${row.id}`)   // ✅ 照旧，字符串插值天然正确
   ```

   后端 `@PathVariable Long` 会自动把 `"2107..."` 剥引号转回 `Long`，
   **不要自己加引号**（`%22...%22` 会 400）。

### 🆕 新增：批量删除 `POST /api/file/batch-delete`

给「文件与产物」面板的**全选 → 一次删完**用的，省掉 N-1 次请求往返。

**请求**

```jsonc
POST /api/file/batch-delete
{
  "ids": ["2107069112529358849", "2107069112529358850"]   // 原样回传列表接口给的 id
}
```

上限 200 个/次，超了返回「单次最多删除 200 个文件」，前端分批发。

**响应 —— 注意是「部分成功」语义**

```jsonc
{
  "code": 0,                       // ← 无论有没有失败，code 都是 0
  "msg": "ok",
  "data": {
    "total": 20,
    "successCount": 18,
    "failCount": 2,
    "deletedIds": ["2107069112529358849", "..."],   // 字符串形态，可直接用来更新面板
    "failedIds":  ["2107069112529358851"]// 不存在 / 不是你的，不区分
  }
}
```

🔴 **前端必须读 `data`，不能只看 `code`**：

```diff
- const res = await axios.post('/api/file/batch-delete', { ids: selectedIds })
- if (res.data.code !== 0) { showError('删除失败') }
- else { refetchList() }
+ const res = await axios.post('/api/file/batch-delete', { ids: selectedIds })
+ const r = res.data.data
+ // 按 deletedIds 精确移除这几行，不要整页刷新（省一次请求，且不闪）
+ setList(prev => prev.filter(f => !r.deletedIds.includes(f.id)))
+ // failedIds 的行留在面板上；有失败时给个非阻塞提示即可，不要整页报错
+ if (r.failCount > 0) toast(`成功删除 ${r.successCount} 个，${r.failCount} 个未删除`)
```

`deletedIds` / `failedIds` 里的 id **和列表接口返回的 id 形态完全一致**
（都是字符串），可以直接 `includes` 比对。

### 删除到底做了什么

1. 先按 `id + user_id` 查库定位（**删不了别人的**，IDOR 防护）；
2. 删数据库记录；
3. **尽力删 OSS 对象** —— 失败只记 WARN，不影响返回值。

所以「记录没了但对象还在」是可能的（凭证失效、URL 解析不出对象名），那只是存储成本。

### 排错：服务端日志

删除落空时后端会打WARN，**两种情况文案不同**（对外统一提示，防探测）：

```
删除文件落空：id=xxx 在 sys_file 中不存在      ← 精度丢失 / 已被删过
删除文件落空：id=xxx 存在但不属于当前用户      ← 越权尝试，安全信号
```

## 2026-10-05：文件/产物删不掉 —— 新增 `DELETE /api/file/{id}`

> ⚠️ **本条已被下一条推翻，根因判断错了。** `bizType` 限制确实是个真问题（已修），
> 但它**不是**「每一行都删不掉」的主因。真正的主因是 **id 精度丢失**，
> 照本条改完仍然会失败。请直接看下面那条。

### 现象

「文件与产物」面板（共 42 个文件 · 对话 13 · 产物 29）里，**每一行点删除都弹「产物不存在或无权删除」**。

### 根因（后端的问题，不是你传错了）

删除端点 `DELETE /api/artifact/{id}` 的 Service 层原来硬加了 `biz_type = 'ARTIFACT'` 条件。
而你的面板是**统一视图** —— 列表里既有 AI 产物（`ARTIFACT`，29 个）也有用户上传的对话附件
（`CHAT`，13 个），删除按钮对所有行打的是同一个端点，于是 `CHAT` 那 13 条**永远命中不了**。

归属校验本来就靠 `user_id`，`biz_type` 不是安全边界，加它只会误伤 —— 已移除。

### 你要动的（1 处）

统一视图的删除按钮改成调新端点：

```diff
- await axios.delete(`/api/artifact/${file.id}`)
+ await axios.delete(`/api/file/${file.id}`)          // ← 不限类型，产物和附件都能删
```

| 端点                       | 状态                                    |
| ------------------------ | ------------------------------------- |
| `DELETE /api/file/{id}`  | ✅ **新增，推荐** —— 不限 `biz_type`，产物/附件/知识库文件都能删 |
| `DELETE /api/artifact/{id}` | ⚠️ 保留，现在与上面**等价**（不再限定 `ARTIFACT`），老代码不会突然失效 |

### 删除到底做了什么

1. 先删 `sys_file` 记录（`id + user_id` 双重匹配，删不了别人的）；
2. 再**尽力删 OSS 对象** —— OSS 删除失败只记 WARN，**不影响返回值**。

所以「记录没了但对象还在」是可能的（凭证失效、URL 解析不出对象名），那只是存储成本，
不会让按钮报错。

### 失败时的文案

| 端点                          | 失败提示            |
| --------------------------- | --------------- |
| `DELETE /api/file/{id}`     | `文件不存在或无权限删除`    |
| `DELETE /api/artifact/{id}` | `产物不存在或无权删除`（未改） |

两种情况（不存在 / 不属于你）后端**刻意不区分**，照着提示展示即可。
想定位具体是哪一种，看服务端日志里新加的 `删除文件落空：id=...` WARN 行。

## 2026-10-05：MCP 预置列表新增 `added` —— 已添加的不能再点「添加」

### 现象

「已添加的服务」里已经有 2 条，「预置服务」里同样的 2 条**还挂着「添加」按钮**，点一下又插一条。

### 根因

`GET /api/mcp/service` 只回模板，**没告诉前端哪个已经添加过**。
前端只能自己拿 `strId` 去比对 `GET /api/mcp` 的结果 —— 而 `strId` 可能是 `null`、空串或带空格
（历史脏数据），比对必然有漏。

### 后端改了什么

`GET /api/mcp/service` 每项新增两个字段：

```jsonc
{
  "strId": "6d9472e117a4",
  "id": "",
  "name": "必应搜索（中文）",
  "url": "https://mcp.api-inference.modelscope.net/6d9472e117a4/mcp",
  "added":    true,        // ← 新增：当前用户是否已添加过这一条
  "localId":  "12",        // ← 新增：已添加时 = mcp_information 主键（字符串）；未添加为 null
  "available": true
}
```

`GET /api/mcp`（已配置列表）里 `added` 恒为 `true`、`localId` 等于自己的 `id` —— 两个接口语义一致。

### 你要动的（1 处）

```diff
- // 预置服务卡片：一律显示「添加」
- <button onClick={() => add(preset)}>添加</button>
+ // 预置服务卡片：后端已经给了答案，不要再自己比对 strId
+ {preset.added
+   ? <button disabled>已添加</button>                      // 或「去编辑」，用 preset.localId
+   : <button onClick={() => add(preset)}>添加</button>}
```

⚠️ **不要**再自己拿 `strId` 去比对 `GET /api/mcp` —— 空串 / `null` / 前后空格都会比对失败，
这正是这个 bug 的来源。

### 后端顺带加固（你不用动）

`POST /api/mcp` 的去重从「只认 `strId`」升级成 **strId → url 两级匹配**。
即使你漏传了 `strId` 也不会再插入重复行 —— 同一个用户 + 同一个服务地址只保留一条。

### 建议先查一下库里有没有已经重复的行

```sql
-- 只读诊断：按 (user_id, str_id) 和 (user_id, url) 分别看重复情况
SELECT user_id, str_id, count(*) AS cnt
FROM   mcp_information
GROUP  BY user_id, str_id
HAVING count(*) > 1;

SELECT user_id, btrim(url) AS url, count(*) AS cnt
FROM   mcp_information
GROUP  BY user_id, btrim(url)
HAVING count(*) > 1;
```

有重复的话，保留 `id` 最小的那条、删掉其余的即可（**先备份或先 `BEGIN;` 再删**）。

## 2026-10-05：乐享接口（`GET /api/lexiang/teams` 等）的 500 变成可读提示

### 现象

`GET /api/lexiang/teams` 一直返回 **500**，前端只看到「Internal Server Error」，不知道为什么。

### 根因

乐享链路抛的全是 `IllegalStateException`（全是**给你看的中文提示**），
但全局异常处理器里**没有为它注册分支** —— 于是全部掉进兜底分支，
变成 `500` + `系统内部错误，请稍后重试或联系管理员`。

换句话说：「你没配凭证」和「服务真的挂了」在前端长得一模一样。

### 现在的行为

仍然是 HTTP 200 + `{code:1, msg:"..."}`（与其它业务异常一致），**但 `msg` 是真实原因**：

| 真实情况                | 现在返回的 `msg`                                    |
| ------------------- | ------------------------------------------------ |

## 2026-10-05：产物归属到「哪一轮」—— 新增 `runId`

**背景（一句话）**
  
以前刷新页面后，AI 产出的文件只能堆在右侧「成果文件」面板里，因为它不知道自己是**哪一轮**产出的。
  
现在给「历史行」和「产物项」都加了同一个 `runId`，前端按字符串相等就能把产物放回产出它的那一轮。

### 后端改了什么

| 接口                             | 变化                                 |
| ------------------------------ | ---------------------------------- |
| `GET /api/history/{sessionId}` | 每行新增 `runId`（String，**可为 `null`**） |
| `GET /api/artifact?sessionId=` | 每项新增 `runId`（String，**可为 `null`**） |

两边是**同一套值**，并且与 SSE `run` 事件信封里的 `runId` 完全一致、会持久化。
  
所以「流式期间按正在生成的那条回答归属」和「刷新后按 `runId` 归属」结果一致 —— 前端不需要缓存任何映射。

### ⚠️ 你要先执行一条 SQL（否则全是 null）

`runId` 是新列，**没跑迁移之前所有行都是 `null`**，你会以为后端没做。

```bash
# 幂等，可重复执行
psql -U hu -d <库名> -f docs/sql/011_add_run_id.sql
```

执行前落库的老数据保持 `null`（不回填），按下面"匹配不上"处理即可。

### 你要动的（3 处）

1. 渲染历史时，消息对象里多存一个 `msg.runId`。
2. 产物先按 `artifact.runId === msg.runId` 内联到对应那一轮；
     
   **匹配不上的保持原样，只进「成果文件」面板**。
3. 去重**仍然按 `id` 或 `url`** —— 一轮可产出多个文件（它们共用同一 `runId`），
     
   且 SSE 期间收到的和刷新后拉回的本来就是同一批。

### 不用动的

- 匹配就是字符串 `===`，**不要**按时间或顺序去猜 —— 猜错会把产物挂到没产出它的那一轮，
    
  比"只在面板里"更糟（对着对话排查问题的人会被误导）。
- `runId` 为 `null`（老数据 / 迁移没跑 / 拿不到 run 信息）→ 跳过匹配，按"只进面板"处理。
- `runId` 不含时间信息、不保证单调，**别拿它排序或推断顺序**。

## 2026-10-05：🔴 `POST /api/chat/model` 请求体**破坏性变更** —— 只传 `configId`

### 改了什么

|     | 旧                                      | 新                       |
| --- | -------------------------------------- | ----------------------- |
| 请求体 | `{ "baseUrl": "...", "token": "..." }` | `{ "configId": "..." }` |
| 路径  | `POST /api/chat/model`                 | **不变**                  |
| 方法  | POST                                   | **不变**                  |
| 响应  | `Result<string[]>`                     | **不变**                  |

### 为什么必须改（这不是前端传错了）

旧的 `token` 字段要前端回传密钥，但**前端手上根本没有明文 Key**：  
`GET /api/user/config` 返回的 `apiKey` 是后端 `UserConfigServiceImpl.decryptKey()`  
拼出来的**打码值**（形如 `sk****3t5d`）。拿它去请求厂商必然 401。

对话（`/api/chat/stream`）、乐享 RAG、MCP Token 三处一直都是后端自己查库解密，  
只有这一个接口要前端回传密钥 —— 现在统一由后端做。

### 前端怎么改

```diff
- await axios.post('/api/chat/model', {
-   baseUrl: selectedConfig.baseUrl,
-   token:   selectedConfig.apiKey,     // ← 打码值，永远 401
- })
+ await axios.post('/api/chat/model', {
+   configId: selectedConfig.id,        // ← user_config 里那条配置的 id
+ })
```

`configId` 就是保存/更新 API 配置时后端生成并返回的那个 `id`，  
前端保存配置响应里能拿到。**不要再传 `baseUrl` 和 `token`。**

### 响应可能变空数组（重要）

后端现在做了**降级**：厂商不支持 `/v1/models`（DeepSeek、小米等都不实现）、  
或 Key 不对、或网络不通时，后端会返回**该配置里用户已保存的模型名**，  
**不会 500**。但如果该配置下一个模型都没存过，就是**空数组 `[]`**。

```jsonc
{
  "code": 200,
  "data": ["Pro", "Flash"]   // 可能是 []，也可能少 —— 都属正常，不要弹错误
}
```

前端要处理：

- `data` 为空数组 → 模型下拉框保持用户当前选择或显示"未获取到模型"，**不要报错**
- 这个接口失败不该阻断页面渲染

### 什么时候会真的失败（会返回错误码，不是空数组）

| 情况                      | 提示文案                    |
| ----------------------- | ----------------------- |
| 没登录                     | 未登录                     |
| 还没配过 API Key            | 尚未配置 API Key，无法查询模型列表   |
| `configId` 不存在或不属于当前用户  | API 配置不存在或不属于当前用户       |
| 加密盐值缺失（脏数据）             | 用户加密盐值缺失，请重新保存一次 API 配置 |
| `baseUrl` 指向内网（SSRF 拦截） | API 配置的 baseUrl 不合法：... |

这些都是 4xx 业务异常，**不是 500**。仍然建议给一个非阻塞的提示。

### 顺带修的（前端无感）

- `application-prod.yml` 里小米 MIMO 的 `baseUrl` 之前误写成阿里的地址  
  （`https://dashscope.aliyuncs.com/compatible-mode/v1`），  
  导致对话时拿小米 Key 敲阿里的门报 401。已改为 `https://api.xiaomimimo.com/v1`。  
  **如果你在页面上选了 MIMO 且报 `Incorrect API key provided`，就是这个原因，已修。**

## 2026-10-05：🔴🔴 AI 交付的文件（docx / xlsx / png / zip）下载后全是坏的

**症状**：点开AI 产出的下载卡片，文件打不开。Word 提示「文件已损坏」、图片显示不出来。
**如果你还遇到这个 —— 后端已修，升级后即恢复；旧链接仍是坏文件，需让 AI 重新生成一次。**

### 这不是前端的问题，是后端把二进制当文本处理了

沙盒里的文件回传 OSS 时，**先按 UTF-8 文本解码、再重新编码**：

```
原始 PNG 头：  89 50 4E 47 0D 0A 1A 0A
损坏后：        EF BF BD 50 4E 47 0D 0A      ← EF BF BD = U+FFFD 的 UTF-8 编码
```

二进制里的非法字节在解码时被替换成 `U+FFFD`（即"�"），
**内容全毁，且每个坏字节从 1 字节涨成 3 字节** —— 这就是当年
「接口说 171196 字节、实际只有 94367 字节」的由来。

docx / xlsx / pptx / zip 同理：它们都是 zip 容器，
任一字节被替换都会让解包直接失败，所以 Office 一律报「已损坏」。

**已修复**：改为按字节读取，不做任何编解码；同时上传时显式带正确的
`Content-Type`（`docx` 不会再被当成裸二进制流）。

### 对前端的影响

| 项 | 说明 |
| --- | --- |
| **接口路径/方法/参数** | 无变化 |
| **响应体字段** | 无变化 |
| **`size` 字段语义** | ⚠️ **变了**：现在等于「文件真实字节数」，与用户下载到的文件大小一致<br>修复前是**损坏后的大小**（偏大）—— 所以旧记录里的 `size` 会比实际文件大 |
| **下载方式** | 无变化，仍是直连 OSS 的 `url` |

### 如果你想在下载卡片上显示大小

`artifact.size` 与 `file.fileSize` 现在都可信了，但**注意它已经是「数字」不是字符串**：

```js
// ✅ 对：Long 被全局序列化成字符串的是「雪花 ID」，size 是 Integer，仍是 number
const size = artifact.size ?? 0
const text = size > 1024 * 1024
  ? `${(size / 1024 / 1024).toFixed(2)} MB`
  : `${Math.ceil(size / 1024)} KB`
```

⚠️ 别对 `size` 用 `Number()` 之外的任何转换，也别对它做精度处理 —— 它远小于
`Number.MAX_SAFE_INTEGER`，就是个普通整数。

### 顺带修的（前端无感）

- OSS 上传时补了 `Content-Type`，`docx` 不再被浏览器当裸流强制下载；
  中文文件名仍做 percent-encoding（老链接不带编码，但依然可用）。
- 沙盒支持自定义模板（`E2B_TEMPLATE_ID`），可预装python-docx / openpyxl / python-pptx / dotnet / 中文字体。
  **这不是前端的事**，只是 AI 生成文档会更稳、不会中途降级手拼 OpenXML。

## 2026-10-06：首字延迟治理（第二轮）—— 记忆窗口大幅收紧

### 为什么要改

线上反馈「首字 4 秒，长会话 21 秒」。排查下来**不是**本机 CPU 或数据库慢
（实测本地前置处理只有 ~100ms 量级），而是**每轮发给模型的历史太大**：

模型在吐第一个字之前，必须先把整个 prompt（历史 + 工具定义 + 系统提示词）
计算一遍（prefill）。历史越长，首字越慢 —— 而且是**越聊越慢**。

### 改了什么（三处，全在后端配置/默认值）

| 项 | 改前 | 改后 | 影响 |
| --- | --- | --- | --- |
| `nexus.agent.memory.max-tokens` | `100000` | `24000` | 每轮最多带 2.4 万 token 的历史（原 10 万） |
| 模型元数据默认 `contextWindow` | `256000` | `65536` | 未填元数据时不再假定超大窗口 |
| 模型元数据默认 `maxOutputTokens` | `32000` | `16384` | 不再把 3.2 万当 `max_tokens` 发给服务商 |
| `deepseek-flash` 的元数据 | `1000000` / `384000` | `65536` / `8192` | 填的是模型**真实**能力 |
| 生产日志级别 | `debug`（prod 未覆盖） | `info`（prod 显式覆盖） | 不再逐条打印 SQL |
| 读历史的条数 | 全量 | 最近 200 条 | 长会话不再拉全量再丢弃 |

### 对前端的影响

| 项 | 说明 |
| --- | --- |
| **接口路径/方法/参数** | 无变化 |
| **响应体字段** | 无变化 |
| **SSE 事件** | 无变化 |
| **模型编辑表单的 placeholder** | ⚠️ **要改**：上下文窗口 `256000` → `65536`；最大输出 `32000` → `16384`<br>（详见 `docs/模型能力配置（前端）.md`，已同步） |
| **长会话行为** | ⚠️ **变了**：超过窗口的更早历史不再进入本次请求，模型可能「不记得」很早以前说过的话 |

### 前端建议配合做的两件事

1. **把「新建会话」做得更显眼**。
   记忆窗口收紧后，一个会话聊太久会开始丢上下文。与其让用户在同一个会话里
   无限聊下去（然后抱怨模型忘事），不如引导他在切换话题时开新会话。

2. **首字之前给一个可信的等待反馈**。
   后端现在已经能给出相对稳定的首字时间，前端不必再用「假进度条」。
   首帧事件里已经有 `runId` / `sessionId`（见 P2-5），可以直接用它做占位。

### 后端新增的可观测日志（排查用，前端不需要处理）

```
CHAT_PREFLIGHT runId=... quota=3ms convert=1ms context=12ms build=8ms total=24ms
CHAT_CONTEXT   runId=... match+model=2ms mcp=0ms skills+aiServices=9ms total=11ms window=24000 ctx=65536 out=8192 tools=15
CHAT_MEMORY    runId=... msgs=18 load=6ms limit=200
CHAT_TTFB      runId=... ttfb=1820ms
```

- `CHAT_PREFLIGHT.total` = 本地前置耗时；`CHAT_TTFB − total` ≈ **模型侧**耗时。
  两者一减就知道慢在我们还是慢在供应商。
- `CHAT_MEMORY.msgs` 撞上 `limit`（默认 200）说明会话已经很长。
- `CHAT_CONTEXT.window` 就是本次最多会带多少 token 的历史 —— 首字慢先看它。

## 2026-10-06：新增「停止生成」接口 + `stopped` SSE 事件 + 技能空数组语义修正

三件事一起改，都是前端要动的。

---

### 1. 新增接口：`POST /api/chat/stop`

用户点「停止生成」时调用。

**请求体**（`runId` 与 `sessionId` 二选一，优先 `runId`）：

```jsonc
{
  "runId": "a1b2c3d4e5f60718",   // ← 首选：SSE 首帧 run 事件的 data.runId
  "sessionId": "……"               // ← 兜底：拿不到 runId 时用，停该会话当前在跑的那次
}
```

**响应**（HTTP 200，失败也是 200 + `code=1`，按 `code !== 0` 弹 `msg` 即可）：

```jsonc
// 成功
{ "code": 0, "msg": "已停止本次生成", "data": "a1b2c3d4e5f60718" }   // data = 被停掉的 runId

// 没在跑 / id 过期（幂等：重复点停止不该报错）
{ "code": 1, "msg": "没有正在进行的生成（可能已经结束，或 runId 已过期）", "data": null }

// 两个都没传
{ "code": 1, "msg": "runId 与 sessionId 至少要传一个（runId 取自 SSE 首帧 run 事件的 data.runId）", "data": null }
```

⚠️ **`runId` 有时效**：只在本次运行期间有效，流结束后就查不到了。
所以要在收到 `run` 首帧时把它存下来（现在应该已经存了 —— 产物归属也靠它）。

**建议的交互**：

1. 「生成中」时显示「停止」按钮；
2. 点它 → 调 `POST /api/chat/stop` → **不要立刻关流**，等 `stopped` 事件回来再收 UI；
3. 若返回 `code=1`（没在跑），说明流已经自己结束了，按 `finish`/`error` 的常规逻辑收尾即可。

---

### 2. 新增 SSE 事件：`stopped`

完整契约见 `docs/sse-contract.md` §3.7，这里只说前端该怎么处理。

```jsonc
{
  "seq": 9,
  "runId": "a1b2…",              // 信封层
  "event": "stopped",            // 事件名
  "data": {
    "reason": "用户停止了本次生成",
    "partial": 1234              // 已生成正文的字符数；> 0 说明回答没写完
  }
}
```

**三条必须遵守的约定**：

| 项 | 说明 |
|---|---|
| **不要弹错误提示** | `stopped` 不是 `error`。用户是主动叫停的，弹红字会让他以为出错了 |
| **要收「生成中」态** | 把 loading / 思考动画关掉，光标停住 |
| **不要触发 `finish` 的后续动作** | 自动滚动到底、自动总结、开启新会话等，都只应在 `finish` 时做 |

**和 `error` 的分流**：

```js
if (event === 'stopped') {
  setGenerating(false)
  if (data.partial > 0) markAnswerIncomplete()   // 可选：提示「回答未完成」
} else if (event === 'error') {
  setGenerating(false)
  showErrorToast(data.message)
} else if (event === 'finish') {
  setGenerating(false)
  onAnswerComplete()                             // 只有这里才触发自动后续动作
}
```

⚠️ **已生成的内容不会丢**：服务端会把叫停时已生成的正文补写进历史，
用户刷新页面仍能看到这一段。

### 3. 语义修正：`ChatDTO.skills` 传空数组 = 不用技能

以前 `skills` 传 `null` 和传 `[]` 是同一个意思（都表示「启用全部技能」）。
这和「技能多选」组件的直觉是**相反**的 —— 用户取消全部勾选，结果后端给他启用了所有技能。

现在的约定：

| 你发的 | 后端的理解 |
|---|---|
| **不传这个字段**（或 `null`） | 启用全部技能（老客户端行为不变） |
| `[]` | **一个都不用**（用户明确表示「这次不要技能」） |
| `["pdf-summarizer"]` | 只启用列出的那几个 |

**前端要改的**：多选组件「全部取消」时，请**照常发空数组**，不要「全不选就干脆不发这个字段」——
后者会被理解成「启用全部」。

## 2026-10-06：「重新生成」成一等公民 —— 后端支持 n/n 版本切换

### 为什么要改

用户反馈：点「重新生成」后刷新页面，会变成两轮独立对话：
```
问题A → 回答A
问题A → 回答B        ← 平铺了
```

期望是 ChatGPT 那种：**一个问题 + 底部 n/n 切换**。

**折叠显示是前端的活，但后端有个更隐蔽的问题**：原来每轮都从库里读**全量**历史，
所以两版回答会**同时进模型上下文** —— 白烧 token、让模型困惑，
而且你切回 1/2 接着聊，模型记得的仍是 2/2 的内容，**切换形同虚设**。

现在后端把这件事做实了。

---

### 1. `GET /api/history/{sessionId}` 的每条消息多了两个字段

```jsonc
{
  "id": "1900000000000000001",   // ← 新增：这条消息的 id，做 n/n 切换的 key 用
  "type": "AI",
  "content": "……",
  "runId": "a1b2…",
  "supersededBy": null            // ← 新增：非 null = 已被更新的回答替代
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | **string** | 这条消息的 id。⚠️ 是**字符串**不是数字 —— 雪花 ID 19 位超出 JS `Number.MAX_SAFE_INTEGER`（16 位），全局序列化成字符串。用它做 key / 比较相等都行，但**不要** `Number()` / `parseInt()` |
| `supersededBy` | string \| null | 非 null = 这条回答已被更新的一版替代（值是替代者的 `id`）。**只是不参与模型上下文，不是删除** —— 照常返回，就是要给你做切换用 |

**折叠规则就一条**：一条 USER 消息后面跟的若干条 AI 消息属于同一组，组内有几条就显示成 `n / n`。

**默认展开哪一个**：展开 `supersededBy == null` 的那个（当前生效的版本）。

> 被替代的行**仍然返回**，只是不参与模型上下文 —— 不返回就没法做切换了。
> 老数据和用户提问行的 `supersededBy` 都是 `null`，按「当前版本」处理即可。

---

### 2. `POST /api/chat/stream` 请求体多了 `regenerateFromMessageId`

点「重新生成」时传它，值就是上面那个 `id`（字符串原样回传）：

```jsonc
{
  "messages": [ /* 和平时一样，本次要发的消息 */ ],
  "sessionId": "……",
  "regenerateFromMessageId": "1900000000000000001"   // ← 新增，可选
}
```

| 你发的 | 后端的行为 |
| --- | --- |
| **不传 / `null`** | 普通发问，行为与本字段出现前**完全一致** |
| 传某个回答的 `id` | 走「重新生成」：**不重复存用户提问**（问题已在库里），并把「从你点的那条回答开始、往后所有还没被替代的旧内容」标记为被本次新回答替代 |

⚠️ **不要自己拼这个 id**，必须从历史接口的 `id` 拿。

**语义说明**：「在 1/2 上重新生成」= 回到旧版本继续开一条新分支，
所以 1/2 之后聊过的内容也一并让位（与 ChatGPT 的分支语义一致，不是缺陷）。

---

### 3. 后端做了什么（你不用管，但影响你看到的现象）

1. **重新生成时不再重复写用户提问** —— 历史里只有一条「问题A」，
   后面挂多个 AI 回答。你按「同一条 USER 后的连续 AI」分组就能折叠。
2. **旧版本被标记 `superseded_by`**，但**仍然返回**给你做切换。
3. **模型上下文只取未被替代的版本** —— 这是让切换真正成立的那一步：
   用户切回 1/2 接着问，模型看到的就真的是 1/2 那一版。

### 1. `finish` / `stopped` / `error` 事件的 `data` 新增 `ttfbMs`

```jsonc
// finish
{ "seq": 13, "runId": "a1b2…", "event": "finish",
  "data": { "status": "DONE", "ttfbMs": 1820 } }

// stopped
{ "seq": 9, "runId": "a1b2…", "event": "stopped",
  "data": { "reason": "用户停止了本次生成", "partial": 1234, "ttfbMs": 950 } }

// error
{ "seq": 7, "runId": "a1b2…", "event": "error",
  "data": { "type": "ERROR", "message": "…", "hint": "…", "ttfbMs": 30000 } }
```

**为什么加**：前端自己测的「首字 xx ms」含网络往返与反代缓冲，与服务端口径对不上表 ——
出现「前端 300ms、服务端日志 1800ms」时两边都以为对方错了。现在给同源的值。

| 项 | 说明 |
| --- | --- |
| 语义 | **从服务端收到请求，到模型吐出第一个内容 token**，与日志 `CHAT_TTFB` 完全同源 |
| 字段缺失 | ⚠️ **可能不存在**（不是 `null`）。模型没吐出内容就结束时不会带这个字段。前端用 `data.ttfbMs ?? 自己测的值` 兜底 |
| 纯思考模型 | 先 thinking 再正文时它会**偏小**。那种场景建议显示「首个 message 事件到达时间」，别用这个数冒充体感延迟 |
| 兼容性 | 纯新增字段，不改动任何已有字段 |

`run` 首帧不带这个字段 —— 那一刻首字还没发生。

### 2. 上传被拒（`code=1`）时 `data` 带配额快照

```jsonc
// POST /api/file/upload 超文件配额
{
  "code": 1,
  "msg": "今日文件与产物数量已达上限（已用 100 / 上限 100），明天 00:00 自动重置。",
  "data": {
    "fileQuota": 100,
    "fileUsed": 100,
    "fileRemaining": 0,
    "fileUnlimited": false,
    "role": "NORMAL"
  }
}
```

**为什么加**：以前只有一句文案，前端只能弹个 toast 然后让用户「再试一次」——
可他根本不知道自己离上限还有多远，下次直接撞墙才知道，等于「突然不让用了」。
有了这份快照就能**提前禁用上传按钮**并显示「还能传 N 个」。

| 项 | 说明 |
| --- | --- |
| 字段名 | 与 `GET /api/user/quota` 的 `QuotaVO` **同名**（`fileQuota`/`fileUsed`/`fileRemaining`/`fileUnlimited`），同一套取值逻辑两处通用 |
| ⚠️ 可能为 `null` | 非配额类拒绝（未登录、配额关闭、统计失败降级放行）时 `data` 仍是 `null`。前端按 `data?.fileRemaining` 兜底 |
| 兼容性 | `code` 仍是 1、HTTP 仍是 200、`msg` 文案不变；只是多了 `data` |

⚠️ **别假设 `data` 一定在** —— 判据用 `code !== 0` 时，`data` 可能是 `null`。

### 3. 确认一件我之前没说清的事：首帧前点停止

fronted 问的：新会话首帧前 `runId` 和 `sessionId` 都拿不到，他的处理是
「先不发，拿到 `runId` 后立刻补发 stop」。

**后端确认：可以，照常停。** 依据是时序——

`register`（把 runId 登记为「可停止」）发生在**请求线程的 preflight 里**，
而首帧是在它之后才发出的。所以「前端拿到 runId」这个时刻，
后端**必然已经登记完了**，此时补发的 stop 一定命中。

> 唯一理论上的空窗是「前端主动发过一次 stop 但 runId 还没登记」——
> 但那时前端根本没发过 `/stream` 请求，无从点停止，实际不可能发生。

幂等无害，你那个「4s 兜底自断」的逻辑留着也对（新会话首帧前那种情况服务端确实收不到）。

## 2026-10-06（晚）：上下文窗口「聊几次就提示新建会话」—— 根因修复 + 真实用量信号

### 用户反馈

> 现在很多模型都是 1M，然后我对话几次就让我 new 窗口了，体验非常不好，怎么可能那么快？
> 而且只是单纯的对话，就算用 agent 产品也不可能那么快窗口上下文就没了。

这个反馈是**对的**，而且比想象中更严重 —— 1M 上下文的模型当时实际只拿到 **2.4 万 token**。

### 根因：prod 里残留的 `max-tokens: 24000` 盖掉了代码默认值

当天上午修首字延迟时把 `nexus.agent.memory.max-tokens` 从 `100000` 调到 `24000`；
下午证明那个因果是错的，把 **Java 默认值**改回 `300000`，但
`application-prod.yml` 里那行 `max-tokens: 24000` **没删**。

profile 属性源的优先级**高于**代码默认值，而 `application.yml` 里 `active: prod` ——
所以线上真正生效的一直是 `24000`：

| 模型 | 声明的上下文 | 实际生效的记忆窗口 | 占声明能力 |
|---|---|---|---|
| `mimo-v2.6-pro` / `flash` | 1,000,000 | **24,000** | 2.4% |
| `deepseek-flash` | 131,072 | **24,000** | 18% |

**这和 2026-10-05 的「任务 2 分钟被掐断」是同一类事故**（prod 残留 `sse.timeout: 120s`），
那次留下了 `SseTimeoutDriftTest`，这次补上 `MemoryWindowDriftTest`。

更值得记的是：**当时三个护栏测试全绿**。原因是它们都用 `new AgentProperties()` 的
**代码默认值**去算生效窗口，从来不读 prod 里写了什么 ——
「读配置文件的测试却读默认值」，等于护栏测了个寂寞。已一并修正。

### 改了什么

| 项 | 改前 | 改后 |
|---|---|---|
| `application-prod.yml` 的 `max-tokens` | `24000`（残留） | **删除该键**，走代码默认 `300000` |
| `application-dev.yml.example` 的 `max-tokens` | `100000`（残留） | **删除该键**（护栏顺带扫出来的第二处漂移） |
| 1M 模型的生效窗口 | 24,000 | **300,000** |
| 前端拿到的用量 | 无，只能数消息条数 | `finish`/`stopped`/`error` 事件带 4 个 `context*` 字段 |

⚠️ **不需要前端改配置、不需要改 DB、不需要重新 build 镜像以外的任何东西** ——
但 `max-tokens` 现在由 jar 内的 `AgentProperties.Memory.maxTokens` 决定，
**要调窗口只能改那个默认值重新打包**（与 `sse.timeout` 同一治理方式）。

### 🟢 前端要改的（这是本次唯一需要你动手的地方）

#### 1. 新增：收尾事件的上下文用量字段

`finish` / `stopped` / `error` 三个事件的 `data` 里新增 **4 个可选字段**：

```jsonc
{
  "status": "DONE",
  "contextWindow": 300000,   // 本次记忆窗口（token）= min(全局上限, 模型窗口 − 输出上限)
  "contextUsed":   12480,    // 本次加载的历史消息估算 token（裁剪前）
  "contextMsgs":   42,       // 本次加载的历史消息条数
  "contextRatio":  0.0416,   // contextUsed / contextWindow，保留 4 位小数
  "ttfbMs":        1820      // 原有字段，未变
}
```

| 字段 | 说明 |
|---|---|
| `contextWindow` | 本次**实际生效**的记忆窗口。不同模型/不同配置下会不一样，**别写死** |
| `contextUsed` | 加载量，发生在窗口裁剪**之前**。`-1` = 没算出来（估算失败），**不是 0** |
| `contextMsgs` | 加载的历史条数（受后端 `max-history-messages=200` 截断） |
| `contextRatio` | 已用比例。**> 1.0 就是「本轮已经开始丢更早的历史」** |

⚠️ 三个事件都带，但**字段是可选的**：后端没登记快照时**不会出现这几个 key**
（刻意不做成 `null`，省你一层判断）。用 `'contextRatio' in data` 判断有没有。

#### 2. 🔴 要改：「长会话引导」不要再按 12 条消息触发

现在的逻辑是前端自己数消息条数、超过 12 条就提示「建议新建会话」。
**这就是用户抱怨的那个提示的直接来源** —— 它跟后端窗口完全脱钩，
后端窗口从 2.4 万放开到 30 万之后，它照样在第 6~7 轮弹出来。

改成用服务端给的真实信号：

```js
// ❌ 旧：跟真实占用毫无关系
if (messages.length > 12) showNewSessionHint()

// ✅ 新：只在真的快撑满 / 已经开始丢历史时才提示
const r = data.contextRatio          // 可能是 undefined（后端没给）
if (r !== undefined && r >= 0.8) {
  // 0.8~1.0：快撑满了，温和提示「可以考虑开个新会话」
  // >= 1.0 ：本轮已经开始丢更早的历史，明确提示
}
```

几个判断要点：

- **没有 `contextRatio` 时不要提示**（老版本后端 / 估算失败），静默即可。
  宁可不提示，也不要再出现「明明还能聊却让我开新窗口」。
- **`contextUsed === -1` 是「没算出来」不是「没用」**，别当成 0 去做除法。
- 阈值建议 `0.8`，别用 1.0 —— 到 1.0 时其实已经丢了历史，提示来得太晚。
- 提示做成**可关闭的**，别每轮都弹。

#### 3. 顺带：模型编辑表单的 placeholder 没变

`contextWindow` 默认 `131072`、`maxOutputTokens` 默认 `32768`（见
`docs/模型能力配置（前端）.md`），本次**未改动**。

但有个新事实值得写进表单的提示里：
**即使把 `contextWindow` 填成 1,000,000，生效窗口也会被全局天花板压到 300,000。**
想用满 1M 需要后端改 `AgentProperties.Memory.maxTokens` 的默认值 —— 这是有意的
（防止误填 10M 把每轮 prefill 拉到几十秒），不是 bug。

### 后端新增的护栏（前端不需要处理）

- `MemoryWindowDriftTest`：禁止任何 yml 再声明 `nexus.agent.memory.max-tokens`；
  并断言 1M 模型的生效窗口不得被砍到声明值的 20% 以下。
- `ProdLatencyGuardTest` 修正：改用 **prod 里实际声明的值**算生效窗口，
  且报错时会区分「卡在全局天花板」还是「卡在模型元数据」（两种修法完全不同）。

两条护栏都做了**反向验证**：把 `24000` 塞回去，两条都确实变红。

## 2026-10-07：上传接口「类型不支持」不再静默消失 + 单次个数上限 10（与 fronted 对齐）

### 起因

fronted 反馈：前端文件选择器没有 `accept` 限制，用户说「什么文件都能传，很离谱」。

**根因不在前端** —— 后端 `FileServiceImpl#uploadFile` 里类型不支持是 `continue`：
文件既不入库也不报错，返回列表里**直接没有它**。前端拿不到任何失败信号，
用户看到的只有「传完了但列表里没这个东西」。加 `accept` 只是掩盖。

### 契约变更（前端要改）

`POST /api/file` 的返回数组 `List<KnowledgeFileVO>`：

| 字段 | 变化 | 说明 |
|---|---|---|
| `uploadStatus` | 已存在，语义不变 | `SUCCESS` / `FAILED` / `PROCESSING`。**现在类型不支持也会返回一条 `FAILED`**（以前这条根本不出现） |
| `failReason` | 已存在 | 给人看的中文原因 |
| **`failCode`** | 🆕 **新增** | 机器可读的失败码，**成功时为 `null`** |

`failCode` 取值（前端请用它分支，**不要匹配 `failReason` 文案**）：

| 值 | 含义 | 前端该做什么 |
|---|---|---|
| `UNSUPPORTED_TYPE` | 扩展名不在白名单 | 提示换格式；文件根本没传，不用重试 |
| `QUOTA_EXCEEDED` | 超出文件/产物配额 | 引导清理或等周期重置，**换格式没用** |
| `TOO_MANY_FILES` | 单次文件数超上限 | 拆批 |
| `FILE_TOO_LARGE` | 单文件超大小（正常由 Spring 拦成 413，这里兜底） | 压缩 |
| `UPLOAD_FAILED` | OSS / IO 失败 | 可重试 |
| `UNKNOWN` | 兜底，不该出现 | — |

⚠️ fronted 的验收要求是「**必须能区分『类型不支持』与『超出配额』**」——
`failCode` 就是为这条加的。两者处理方式完全不同（换格式 vs 清理空间）。

### 行为变化一览

| 情形 | 改前 | 改后 |
|---|---|---|
| 类型不支持 | 静默消失，返回列表里没有 | 返回一条 `FAILED` 记录，带 `failCode=UNSUPPORTED_TYPE` |
| 单次文件数 > 10 | 无限制 | **整批拒绝**：`ValidationException` → HTTP 200 + `code=1`，msg 带上限数值 |
| 大小超限 | 413（不变） | 413（不变） |
| 配额超限 | 200 + `code=1`（不变） | 不变 |
| OSS 失败 | 已有 FAILED 记录 | 不变，另补 `failCode=UPLOAD_FAILED` |

**A 方案（fronted 选的）**：坏文件不毁整批 —— 一个不支持的文件只会让**它自己**变成
`FAILED`，同批其他文件照常上传成功。所以前端不要因为数组里有 `FAILED` 就整页报错。

### 前端要做的两件事

1. **渲染失败行**：文件列表里按 `uploadStatus === 'FAILED'` 渲染 `failReason`
   （fronted 说 SysFileVO 侧已在渲染，直接复用同一结构即可）。
2. **选择器加 `accept`**（体验优化，不是替代后端）：
   `accept=".txt,.md,.markdown,.html,.htm,.csv,.doc,.docx,.xls,.xlsx,.ppt,.pptx,.pdf,.one,.jpg,.jpeg,.png,.gif,.webp"`
   并在超过 10 个时直接拦下提示。

⚠️ 后端**也**会拦 10 个（第二道防线）—— 前端的拦截是体验，不是安全边界。

### 后端侧

- 新增 `em/UploadFailCode`、`AgentProperties.Upload.maxCount`（默认 10）
- `SysFile.failCode` 用 `@TableField(exist = false)` —— **不入库、不需要执行 SQL**
- 新增 `FileServiceUploadRejectTest`(5)，**已反向验证**：把实现改回 `continue`，两条用例立刻变红

2. **别假设工具 id 连续、别假设数量配对** —— 收到的 id 本来就是稀疏的。
3. **存量数据**：过滤发生在读历史时，所以**老会话里的 `create_box` 也不会再返回**；

## 2026-10-07（晚 2）：🔴 工具 `id` 不可用作列表 key —— 新增 `index`，历史侧兜底合成 id

> 起因：frontend 报「点历史记录后整个应用卡死」，根因是**工具卡列表用 `call.id` 做 `v-for` key**，
> 而 `id` 缺失/重复 → key 撞车 → Vue patch 拿到 null el → `Cannot set properties of null (setting '__vnode')`。
> 他在前端侧已修（唯一 id 就地生成 + key 下标兜底）；下面是**后端侧的配套根治**，请一并接上。

### 1. 契约澄清（这条最重要）

`toolRequestList[].id` 与 `toolResultVO.id` 都是**模型/供应商给的字符串，后端原样透传**：

- 流式帧里**除首帧外 `id` 常常为 `null`**；
- 某些供应商的兼容层**完全不回传 tool_call id**，同一批里多条都是 `null`；
- 历史接口同样可能拿到 `null`。

所以：**`id` 只能用于"尽力配对"，绝不能当列表 key**。

### 2. 新增 `index`（`tool_execution` 事件）

`toolRequestList[]` 每项新增 **`index`**（整数，可选）：同一批并行调用里的 `0,1,2…`，
**稳定唯一、首帧就有、不会为 null**。

```jsonc
{"type":"TOOL_EXECUTION","toolRequestList":[{"id":null,"toolName":"execute_code","arguments":"{\"co","index":1}]}
```

做 key 请用 `index`；需要跨消息全局唯一时用 `消息id + index`。

⚠️ 该字段**只有 SSE 有，历史接口没有** —— 历史消息是 langchain4j 序列化的，
`ToolExecutionRequest` 里不含 index（历史侧改用下面的兜底）。

### 3. 历史侧：id 缺失时后端兜底合成

`GET /api/history/{sessionId}` 里，若工具 `id` 为 null/空白，后端合成一个**全局唯一** id：

```
row-<该行主键>#<序号>      例：row-1002#0、row-1002#1
```

带行主键，所以即便把不同消息的工具卡铺进同一个列表也不会撞。
（只在展示层补，`chat_memory` 里那条消息保持原样 —— 动了会破坏模型侧的配对语义。）

### 4. 另一条容易漏的：工具调用挂在哪一行

工具调用请求挂在 **AI 行的 `toolRequestList`** 上，**不是**独立的 `TOOL_EXECUTION` 类型行。
frontend 以前只认 `TOOL_EXECUTION` → 历史里的工具卡丢了参数、只剩孤儿结果（他已改为 AI 行也消费）。

### 5. 前端要做的

1. 列表 key 换成 `index`（或 `消息id + index`），`id` 只做尽力配对；
2. 渲染时**同时消费 AI 行的 `toolRequestList`**（思考 → 工具 → 正文的落位）；
3. 配对失败要能容错（有 result 找不到 request 时不渲染而不是崩）。

### 6. 后端侧

- `MessageVO.ToolRequestVO` 新增 `index`；`SseResponseConverter#writeToolRequestWithStream` 下发
- `ChatMemoryServiceImpl#ensureToolIds` —— 历史合成 id（展示层，不动库）
- 契约写入 `docs/sse-contract.md` §3.3 / §3.4
- 新增 2 条用例：流式帧带 index（含 `id=null` 情形）、历史空 id 合成后全局唯一

## 2026-10-07（晚 6）：🔴 自带 Key 不再被平台配额拦 + 配额超限走 SSE `error`（前端终于能看到原因）

> 用户原话：「配额用完咋不拦截一下请求，然后返回正确的信息，你看这前端的信息对吗？
> **生成失败：服务异常，请稍后重试**」/「为啥用自己的模型还报额度没了的错」

### 1. 自带 Key 时不再校验平台 token 配额

以前 `chat()` 开头**无条件** `assertWithinQuota(userId)` —— 用户配置自己的 API Key 时，
费用由他自己的供应商账号承担，平台却拿平台额度拦他（额度是他之前用系统模型耗掉的）。

现在：只有**用系统内置模型**（平台 Key）时才校验 token 配额。
判定复用与"实际用谁的 Key"同一套匹配逻辑，保证不会出现"判定放行、实际走平台 Key"的漏拦。

⚠️ **文件/产物配额（每日条数）仍然生效** —— 那是平台存储资源，与 Key 无关。

### 2. 配额超限：走 SSE `error` 事件，前端能看到真实原因

🔴 **这是「服务异常，请稍后重试」的根因**：`/api/chat/stream` 是 SSE 请求，
但 preflight 阶段的业务异常经 `GlobalExceptionHandler` 变成了 **JSON** 返回 ——
而前端用 `EventSource`，**只解析 SSE 帧**，于是只能自己兜底成通用文案。

现在配额校验移到首帧之后，超限时：

```
event: run      ← 先给 sessionId/runId（前端拿得到）
event: error    ← data.message = "您的 token 配额已用完（已用 X / 上限 Y）…"
```

### 3. 前端要改的一处

**收到 `error` 事件时，请展示 `data.message` 的原文**，不要一律替换成「服务异常，请稍后重试」。

配额/解密/模型找不到这几类错误的 msg 都是给人看的具体原因（自带 Key 的用户之前就是被
「平台额度用完」这种错误信息误导，才以为是自己 Key 的问题）。`data.hint` 可能也在，
按需展示。

### 4. 后端侧

- `ChatContextFactory#usesUserProvidedModel`（新增，判定自带 Key）
- `ChatServiceImpl`：`assertWithinQuota` 移到 `writer.start()` 之后，且仅在用平台 Key 时执行；
  超限 → `writer.onError(e)` + 返回 emitter（前端能收到 `error` 帧）
- 新增 `ChatContextFactoryOwnKeyTest`(4)：自带 Key 识别 / 无配置 / 未指定模型 / userId 为空

## 2026-10-07（晚 7）：`GET /api/chat/model` 补了兼容入口（405 会伪装成"服务异常"）

### 背景
2026-10-05 把这个接口从 GET 改成 POST（不再回传密钥），但**没保留 GET**。
前端若还没改过来 → **405 Method Not Allowed**，而 405 在多数前端框架里被兜底成
「服务异常，请稍后重试」—— 排查时压根看不出是请求方法不对。

### 变更
新增 `GET /api/chat/model?configId=xxx`，行为与 POST 完全一致（内部委托给同一个方法）。

⚠️ **仍然建议改用 POST**：`configId` 放 URL 里会进浏览器历史与 access log。
这个入口只是兜底 —— 每次被调用都会打一条 WARN 日志，确认迁移完成后后端会删掉。

### 前端要做的
请确认你们调的是 **POST + JSON body**（`{ "configId": "xxx" }`）。
如果之前一直"模型列表取不到"，八成就是这里。
