## 2026-10-06：用户分级配额（NORMAL / TEST / VIP）+ 长期记忆写不进库的修复 + 首字延迟治理

> 配套迁移：**`docs/sql/012_add_user_role_and_file_quota.sql`（需人工执行）**。
> 没执行也能跑：后端三处配额校验都做了「查库失败就降级放行」，不会把接口打挂，
> 但**额度不会生效**，且 `GET /api/user/quota` 会返回 `degraded=true`。

### 1. 唯一需要你改的：`GET /api/user/quota` 多了 4 个字段

响应体在原有字段基础上新增（**老字段一个都没动，是纯增量**）：

```jsonc
{
  "code": 0,
  "data": {
    // ===== 原有字段（不变）=====
    "quota": 1000000,          // token 上限；不限制时为 null
    "used": 12345,
    "remaining": 987655,       // 不限制时为 null
    "unlimited": false,
    "period": "DAILY",         // NONE / DAILY / MONTHLY
    "periodStart": "2026-10-06T00:00:00",
    "degraded": false,

    // ===== 2026-10-06 新增 =====
    "role": "NORMAL",          // 新增：NORMAL / TEST / VIP
    "fileQuota": 100,          // 新增：今日「文件 + 产物」条数上限；不限制时为 null
    "fileUsed": 3,             // 新增：今日已产生条数；统计失败时为 null
    "fileRemaining": 97,       // 新增：不限制时为 null
    "fileUnlimited": false     // 新增：是否不限量
  }
}
```

**可空字段的兜底（必须按这个来，否则会显示错）**

| 字段 | 何时为 `null` | 前端怎么兜底 |
| --- | --- | --- |
| `fileQuota` / `fileRemaining` | 该用户**不限制**文件数量（TEST 档，或运营把 `users.file_quota` 置空） | 显示「不限」，**不要**显示 `0 / 100` 这种假数字 |
| `fileUsed` | 统计 `sys_file` 失败（库异常） | 显示 `--`，**不要**当 0 —— 0 会被读成「今天一个都没用」，与事实可能相反 |
| `role` | 库里还没跑 `012`（该列不存在）时**整个 `data` 会是 `degraded=true` 的占位体** | 见下 |

⚠️ `degraded === true` 时**其余全部字段都不可信**，请统一显示「配额信息暂不可用」，
不要把 `null` 渲染成 `0`。

**展示建议（不是必须）**：设置页或账号区可以显示「今日文件与产物 3 / 100」。
⚠️ 但**判断「还能不能传」不要看 `role`** —— 运营可以单独改某人的 `users.file_quota`，
那时 `role` 是 `NORMAL` 而额度是 200。判断一律看 `fileUnlimited` 与 `fileRemaining`。

### 2. 上传超限：接口会返回 `code=1`（HTTP 仍是 200）

`POST /api/file/upload`（以及其它上传端点）在超出今日额度时：

```jsonc
{
  "code": 1,
  "msg": "今日文件与产物数量已达上限（已用 100 / 上限 100），明天 00:00 自动重置。",
  "data": null
}
```

- **HTTP 状态码是 200**，按 `code !== 0` 判断失败（与全站其它业务失败一致）；
- 直接把 `msg` 弹给用户即可，文案里已带上「已用 / 上限 / 什么时候恢复」；
- 拦截发生在**传到 OSS 之前**，超限不会产生任何存储请求，可以放心让用户重试。

### 3. AI 产物（artifact）超限：没有新事件，前端不用改

`publish_artifact` 在超限时会被后端直接拒绝，**不会**推 `artifact` 事件。
模型会收到结构化失败（`errorCode: QUOTA_EXCEEDED`）并用**普通文字**告诉用户。
所以产物卡片逻辑、SSE 事件契约**一律不变**（见 `docs/sse-contract.md`）。

### 4. 你无感的后端改动（不用改代码，但知道一下排查时有用）

| 改动 | 说明 |
| --- | --- |
| **长期记忆终于能写进库了** | 根因：工具跑在流式回调线程，`UserContextHolder` 恒为 `null` → `user_id` 为 `null` → 撞 `user_memory.user_id NOT NULL`；而写库方法是 `@Async`，异常被吞 → 工具照样返回 `ok`。现在改用 `RunUserRegistry` 反查 userId、去掉 `@Async`、取不到用户就明确报错。 |
| **首字延迟治理** | 每轮对话都在重建 HTTP 连接池（真凶），已改为按指纹缓存模型实例；`matchModel` 从 1 次请求调 3 次降到 1 次；SSE 加了 `X-Accel-Buffering: no`。前端无需改动。 |
| **`download_file` / `publish_artifact` 的 OSS 归属** | 以前这两个工具传给沙盒的 `user_id` 恒为空（同一个 ThreadLocal 坑），OSS 对象不归属任何用户。现在传真实 userId。 |
| **注册即按角色写额度** | 新用户：`role=NORMAL`、`token_quota=1000000`、`token_period=DAILY`、`file_quota=100`。 |

## 2026-10-05：🔴🔴 文件还是删不掉 —— 真凶是 id 精度丢失（上一轮结论是错的）+ 新增批量删除

### 先纠正上一条

上一条说根因是 `bizType=ARTIFACT` 限制 —— **那个只是次要问题，删掉它不解决问题**。
删掉之后你反馈「还是每次都这样」，是对的。真凶在下面。

### 真凶：19 位雪花 ID 在浏览器里被四舍五入

`sys_file.id` 是雪花 ID，**19 位十进制数**（如 `2107069112529358849`）。
而 JavaScript 的 `number` 是 IEEE754 双精度浮点，能精确表示的整数上限是
`Number.MAX_SAFE_INTEGER = 9007199254740991`，只有 **16 位**。

```jsonc
// 后端返回（修复前）
{ "id": 2107069112529358849 }

// 浏览器 JSON.parse 之后 —— 低位被抹掉
{ "id": 2107069112529358848 }   // ← 差 1，已经不是同一个 id 了
```

实测抽样 4000 个雪花 ID，**99.6% 会被改写**。

删除是「按 id 回传」的操作，链路是
`后端返回 id → 浏览器 double → 前端拼 URL → 后端 WHERE id = ?`，
id 在浏览器里已经变了，**后端必然查不到**，于是每一行都返回
「文件不存在或无权限删除」。

⚠️ **这个坑不只影响删除**：凡是「拿 id 去改 / 删」的接口都会中招
（技能、用户记忆、MCP、聊天记录…）。已在后端统一根治。

### 后端改了什么

**所有 `Long` 字段现在序列化成字符串**（`Integer` 不变）。

```jsonc
// 修复后
{
  "id": "2107069112529358849",     // ← 带引号
  "userId": "7",
  "fileSize": "1048576",           // ← Long，也变字符串
  "code": 0                        // ← Integer，保持数字不变
}
```

| 字段类型 | 之前 | 现在 |
| --- | --- | --- |
| `Long` / `long`（id、userId、**fileSize**、total…） | 数字 | **字符串** |
| `Integer` / `int`（`code`、分页条数…） | 数字 | 数字（**没变**） |

`code` 保持数字很重要 —— `res.code !== 0` 这类判断不能失效。

⚠️ **`fileSize` 也变字符串了**（它是 `Long`）。如果你有按大小排序或格式化的代码：

```diff
- list.sort((a, b) => a.fileSize - b.fileSize)          // 字符串相减 = NaN，排序乱掉
+ list.sort((a, b) => Number(a.fileSize) - Number(b.fileSize))   // 排序时转数字

- formatSize(file.fileSize)                             // 若函数内部做除法，记得 Number()
+ formatSize(Number(file.fileSize))
```

> 为什么不把 `fileSize` 排除掉？因为它**可能**超过 2^53（2PB），只是现实中不会。
> 统一按类型处理，规则简单可靠；真要单独豁免，就得给每个 VO 字段加注解，
> 那正是这次要避免的「治标」做法。**排序/算术时 `Number()` 转一下即可。**

### 🔴 受影响的字段完整清单（不止文件）

除了所有 `id` / `userId`，这些也会变成字符串，**前端如果拿它们做算术会静默出错**：

| 字段 | 出现在 | 典型用法 | 处理|
| --- | --- | --- | --- |
| `fileSize` | `GET /api/file`、`GET /api/artifact`、SSE 产物、历史消息附件 | 排序、大小格式化 | `Number()` |
| `quota` / `used` / `remaining` | `GET /api/user/quota`（`QuotaVO`） | **进度条百分比**、`used / quota` | `Number()` |
| `tokenQuota` / `tokenUsed` | `GET /api/user/config` |同上 | `Number()` |
| `total` | `Result` 包装 | 分页总数 | 一般只显示，不用算 |

```diff
- <Progress percent={used / quota * 100} />          // 字符串相除 = NaN，进度条变空白
+ <Progress percent={Number(used) / Number(quota) * 100} />
```

⚠️ **这类 bug 不会报错**，只会「数字不显示 / 进度条空白 / 排序乱」，
很容易被当成样式问题排查半天。所以请把上面几个字段全仓搜一遍。

### 你要检查的（2 处）

1. **如果代码里有 `Number(id)` / `parseInt(id)` / `+id`，全部删掉。**
   现在 id 已经是精确的字符串，再转数字等于主动把精度搞坏：

   ```diff
   - const id = Number(row.id)
   - const id = parseInt(row.id, 10)
   + const id = row.id            // ← 直接用字符串
   ```

2. **如果代码里有 id 的大小比较或算术，同样不能用。**
   比如 `if (id > 1000)` 换成 `if (String(id).length > 3)`，
   或者干脆改用 `runId` 这类字符串字段做判断。

3. **拼 URL 的地方不用改。** 直接把字符串插进去即可：

   ```js
   axios.delete(`/api/file/${row.id}`)   // ✅ 照旧，字符串插值天然正确
   ```

   后端 `@PathVariable Long` 会自动把 `"2107..."` 剥引号转回 `Long`，
   **不要自己加引号**（`%22...%22` 会 400）。

### 🆕 新增：批量删除 `POST /api/file/batch-delete`

给「文件与产物」面板的**全选 → 一次删完**用的，省掉 N-1 次请求往返。

**请求**

```jsonc
POST /api/file/batch-delete
{
  "ids": ["2107069112529358849", "2107069112529358850"]   // 原样回传列表接口给的 id
}
```

上限 200 个/次，超了返回「单次最多删除 200 个文件」，前端分批发。

**响应 —— 注意是「部分成功」语义**

```jsonc
{
  "code": 0,                       // ← 无论有没有失败，code 都是 0
  "msg": "ok",
  "data": {
    "total": 20,
    "successCount": 18,
    "failCount": 2,
    "deletedIds": ["2107069112529358849", "..."],   // 字符串形态，可直接用来更新面板
    "failedIds":  ["2107069112529358851"]// 不存在 / 不是你的，不区分
  }
}
```

🔴 **前端必须读 `data`，不能只看 `code`**：

```diff
- const res = await axios.post('/api/file/batch-delete', { ids: selectedIds })
- if (res.data.code !== 0) { showError('删除失败') }
- else { refetchList() }
+ const res = await axios.post('/api/file/batch-delete', { ids: selectedIds })
+ const r = res.data.data
+ // 按 deletedIds 精确移除这几行，不要整页刷新（省一次请求，且不闪）
+ setList(prev => prev.filter(f => !r.deletedIds.includes(f.id)))
+ // failedIds 的行留在面板上；有失败时给个非阻塞提示即可，不要整页报错
+ if (r.failCount > 0) toast(`成功删除 ${r.successCount} 个，${r.failCount} 个未删除`)
```

`deletedIds` / `failedIds` 里的 id **和列表接口返回的 id 形态完全一致**
（都是字符串），可以直接 `includes` 比对。

### 删除到底做了什么

1. 先按 `id + user_id` 查库定位（**删不了别人的**，IDOR 防护）；
2. 删数据库记录；
3. **尽力删 OSS 对象** —— 失败只记 WARN，不影响返回值。

所以「记录没了但对象还在」是可能的（凭证失效、URL 解析不出对象名），那只是存储成本。

### 排错：服务端日志

删除落空时后端会打WARN，**两种情况文案不同**（对外统一提示，防探测）：

```
删除文件落空：id=xxx 在 sys_file 中不存在      ← 精度丢失 / 已被删过
删除文件落空：id=xxx 存在但不属于当前用户      ← 越权尝试，安全信号
```

## 2026-10-05：文件/产物删不掉 —— 新增 `DELETE /api/file/{id}`

> ⚠️ **本条已被下一条推翻，根因判断错了。** `bizType` 限制确实是个真问题（已修），
> 但它**不是**「每一行都删不掉」的主因。真正的主因是 **id 精度丢失**，
> 照本条改完仍然会失败。请直接看下面那条。

### 现象

「文件与产物」面板（共 42 个文件 · 对话 13 · 产物 29）里，**每一行点删除都弹「产物不存在或无权删除」**。

### 根因（后端的问题，不是你传错了）

删除端点 `DELETE /api/artifact/{id}` 的 Service 层原来硬加了 `biz_type = 'ARTIFACT'` 条件。
而你的面板是**统一视图** —— 列表里既有 AI 产物（`ARTIFACT`，29 个）也有用户上传的对话附件
（`CHAT`，13 个），删除按钮对所有行打的是同一个端点，于是 `CHAT` 那 13 条**永远命中不了**。

归属校验本来就靠 `user_id`，`biz_type` 不是安全边界，加它只会误伤 —— 已移除。

### 你要动的（1 处）

统一视图的删除按钮改成调新端点：

```diff
- await axios.delete(`/api/artifact/${file.id}`)
+ await axios.delete(`/api/file/${file.id}`)          // ← 不限类型，产物和附件都能删
```

| 端点                       | 状态                                    |
| ------------------------ | ------------------------------------- |
| `DELETE /api/file/{id}`  | ✅ **新增，推荐** —— 不限 `biz_type`，产物/附件/知识库文件都能删 |
| `DELETE /api/artifact/{id}` | ⚠️ 保留，现在与上面**等价**（不再限定 `ARTIFACT`），老代码不会突然失效 |

### 删除到底做了什么

1. 先删 `sys_file` 记录（`id + user_id` 双重匹配，删不了别人的）；
2. 再**尽力删 OSS 对象** —— OSS 删除失败只记 WARN，**不影响返回值**。

所以「记录没了但对象还在」是可能的（凭证失效、URL 解析不出对象名），那只是存储成本，
不会让按钮报错。

### 失败时的文案

| 端点                          | 失败提示            |
| --------------------------- | --------------- |
| `DELETE /api/file/{id}`     | `文件不存在或无权限删除`    |
| `DELETE /api/artifact/{id}` | `产物不存在或无权删除`（未改） |

两种情况（不存在 / 不属于你）后端**刻意不区分**，照着提示展示即可。
想定位具体是哪一种，看服务端日志里新加的 `删除文件落空：id=...` WARN 行。

## 2026-10-05：MCP 预置列表新增 `added` —— 已添加的不能再点「添加」

### 现象

「已添加的服务」里已经有 2 条，「预置服务」里同样的 2 条**还挂着「添加」按钮**，点一下又插一条。

### 根因

`GET /api/mcp/service` 只回模板，**没告诉前端哪个已经添加过**。
前端只能自己拿 `strId` 去比对 `GET /api/mcp` 的结果 —— 而 `strId` 可能是 `null`、空串或带空格
（历史脏数据），比对必然有漏。

### 后端改了什么

`GET /api/mcp/service` 每项新增两个字段：

```jsonc
{
  "strId": "6d9472e117a4",
  "id": "",
  "name": "必应搜索（中文）",
  "url": "https://mcp.api-inference.modelscope.net/6d9472e117a4/mcp",
  "added":    true,        // ← 新增：当前用户是否已添加过这一条
  "localId":  "12",        // ← 新增：已添加时 = mcp_information 主键（字符串）；未添加为 null
  "available": true
}
```

`GET /api/mcp`（已配置列表）里 `added` 恒为 `true`、`localId` 等于自己的 `id` —— 两个接口语义一致。

### 你要动的（1 处）

```diff
- // 预置服务卡片：一律显示「添加」
- <button onClick={() => add(preset)}>添加</button>
+ // 预置服务卡片：后端已经给了答案，不要再自己比对 strId
+ {preset.added
+   ? <button disabled>已添加</button>                      // 或「去编辑」，用 preset.localId
+   : <button onClick={() => add(preset)}>添加</button>}
```

⚠️ **不要**再自己拿 `strId` 去比对 `GET /api/mcp` —— 空串 / `null` / 前后空格都会比对失败，
这正是这个 bug 的来源。

### 后端顺带加固（你不用动）

`POST /api/mcp` 的去重从「只认 `strId`」升级成 **strId → url 两级匹配**。
即使你漏传了 `strId` 也不会再插入重复行 —— 同一个用户 + 同一个服务地址只保留一条。

### 建议先查一下库里有没有已经重复的行

```sql
-- 只读诊断：按 (user_id, str_id) 和 (user_id, url) 分别看重复情况
SELECT user_id, str_id, count(*) AS cnt
FROM   mcp_information
GROUP  BY user_id, str_id
HAVING count(*) > 1;

SELECT user_id, btrim(url) AS url, count(*) AS cnt
FROM   mcp_information
GROUP  BY user_id, btrim(url)
HAVING count(*) > 1;
```

有重复的话，保留 `id` 最小的那条、删掉其余的即可（**先备份或先 `BEGIN;` 再删**）。

## 2026-10-05：乐享接口（`GET /api/lexiang/teams` 等）的 500 变成可读提示

### 现象

`GET /api/lexiang/teams` 一直返回 **500**，前端只看到「Internal Server Error」，不知道为什么。

### 根因

乐享链路抛的全是 `IllegalStateException`（全是**给你看的中文提示**），
但全局异常处理器里**没有为它注册分支** —— 于是全部掉进兜底分支，
变成 `500` + `系统内部错误，请稍后重试或联系管理员`。

换句话说：「你没配凭证」和「服务真的挂了」在前端长得一模一样。

### 现在的行为

仍然是 HTTP 200 + `{code:1, msg:"..."}`（与其它业务异常一致），**但 `msg` 是真实原因**：

| 真实情况                | 现在返回的 `msg`                                    |
| ------------------- | ------------------------------------------------ |

## 2026-10-05：产物归属到「哪一轮」—— 新增 `runId`

**背景（一句话）**  
以前刷新页面后，AI 产出的文件只能堆在右侧「成果文件」面板里，因为它不知道自己是**哪一轮**产出的。  
现在给「历史行」和「产物项」都加了同一个 `runId`，前端按字符串相等就能把产物放回产出它的那一轮。

### 后端改了什么

| 接口                             | 变化                                 |
| ------------------------------ | ---------------------------------- |
| `GET /api/history/{sessionId}` | 每行新增 `runId`（String，**可为 `null`**） |
| `GET /api/artifact?sessionId=` | 每项新增 `runId`（String，**可为 `null`**） |

两边是**同一套值**，并且与 SSE `run` 事件信封里的 `runId` 完全一致、会持久化。  
所以「流式期间按正在生成的那条回答归属」和「刷新后按 `runId` 归属」结果一致 —— 前端不需要缓存任何映射。

### ⚠️ 你要先执行一条 SQL（否则全是 null）

`runId` 是新列，**没跑迁移之前所有行都是 `null`**，你会以为后端没做。

```bash
# 幂等，可重复执行
psql -U hu -d <库名> -f docs/sql/011_add_run_id.sql
```

执行前落库的老数据保持 `null`（不回填），按下面"匹配不上"处理即可。

### 你要动的（3 处）

1. 渲染历史时，消息对象里多存一个 `msg.runId`。
2. 产物先按 `artifact.runId === msg.runId` 内联到对应那一轮；     
   **匹配不上的保持原样，只进「成果文件」面板**。
3. 去重**仍然按 `id` 或 `url`** —— 一轮可产出多个文件（它们共用同一 `runId`），     
   且 SSE 期间收到的和刷新后拉回的本来就是同一批。

### 不用动的

- 匹配就是字符串 `===`，**不要**按时间或顺序去猜 —— 猜错会把产物挂到没产出它的那一轮，    
  比"只在面板里"更糟（对着对话排查问题的人会被误导）。
- `runId` 为 `null`（老数据 / 迁移没跑 / 拿不到 run 信息）→ 跳过匹配，按"只进面板"处理。
- `runId` 不含时间信息、不保证单调，**别拿它排序或推断顺序**。

## 2026-10-05：🔴 `POST /api/chat/model` 请求体**破坏性变更** —— 只传 `configId`

### 改了什么

|     | 旧                                      | 新                       |
| --- | -------------------------------------- | ----------------------- |
| 请求体 | `{ "baseUrl": "...", "token": "..." }` | `{ "configId": "..." }` |
| 路径  | `POST /api/chat/model`                 | **不变**                  |
| 方法  | POST                                   | **不变**                  |
| 响应  | `Result<string[]>`                     | **不变**                  |

### 为什么必须改（这不是前端传错了）

旧的 `token` 字段要前端回传密钥，但**前端手上根本没有明文 Key**：  
`GET /api/user/config` 返回的 `apiKey` 是后端 `UserConfigServiceImpl.decryptKey()`  
拼出来的**打码值**（形如 `sk****3t5d`）。拿它去请求厂商必然 401。

对话（`/api/chat/stream`）、乐享 RAG、MCP Token 三处一直都是后端自己查库解密，  
只有这一个接口要前端回传密钥 —— 现在统一由后端做。

### 前端怎么改

```diff
- await axios.post('/api/chat/model', {
-   baseUrl: selectedConfig.baseUrl,
-   token:   selectedConfig.apiKey,     // ← 打码值，永远 401
- })
+ await axios.post('/api/chat/model', {
+   configId: selectedConfig.id,        // ← user_config 里那条配置的 id
+ })
```

`configId` 就是保存/更新 API 配置时后端生成并返回的那个 `id`，  
前端保存配置响应里能拿到。**不要再传 `baseUrl` 和 `token`。**

### 响应可能变空数组（重要）

后端现在做了**降级**：厂商不支持 `/v1/models`（DeepSeek、小米等都不实现）、  
或 Key 不对、或网络不通时，后端会返回**该配置里用户已保存的模型名**，  
**不会 500**。但如果该配置下一个模型都没存过，就是**空数组 `[]`**。

```jsonc
{
  "code": 200,
  "data": ["Pro", "Flash"]   // 可能是 []，也可能少 —— 都属正常，不要弹错误
}
```

前端要处理：

- `data` 为空数组 → 模型下拉框保持用户当前选择或显示"未获取到模型"，**不要报错**
- 这个接口失败不该阻断页面渲染

### 什么时候会真的失败（会返回错误码，不是空数组）

| 情况                      | 提示文案                    |
| ----------------------- | ----------------------- |
| 没登录                     | 未登录                     |
| 还没配过 API Key            | 尚未配置 API Key，无法查询模型列表   |
| `configId` 不存在或不属于当前用户  | API 配置不存在或不属于当前用户       |
| 加密盐值缺失（脏数据）             | 用户加密盐值缺失，请重新保存一次 API 配置 |
| `baseUrl` 指向内网（SSRF 拦截） | API 配置的 baseUrl 不合法：... |

这些都是 4xx 业务异常，**不是 500**。仍然建议给一个非阻塞的提示。

### 顺带修的（前端无感）

- `application-prod.yml` 里小米 MIMO 的 `baseUrl` 之前误写成阿里的地址  
  （`https://dashscope.aliyuncs.com/compatible-mode/v1`），  
  导致对话时拿小米 Key 敲阿里的门报 401。已改为 `https://api.xiaomimimo.com/v1`。  
  **如果你在页面上选了 MIMO 且报 `Incorrect API key provided`，就是这个原因，已修。**

## 2026-10-05：🔴🔴 AI 交付的文件（docx / xlsx / png / zip）下载后全是坏的

**症状**：点开AI 产出的下载卡片，文件打不开。Word 提示「文件已损坏」、图片显示不出来。
**如果你还遇到这个 —— 后端已修，升级后即恢复；旧链接仍是坏文件，需让 AI 重新生成一次。**

### 这不是前端的问题，是后端把二进制当文本处理了

沙盒里的文件回传 OSS 时，**先按 UTF-8 文本解码、再重新编码**：

```
原始 PNG 头：  89 50 4E 47 0D 0A 1A 0A
损坏后：        EF BF BD 50 4E 47 0D 0A      ← EF BF BD = U+FFFD 的 UTF-8 编码
```

二进制里的非法字节在解码时被替换成 `U+FFFD`（即"�"），
**内容全毁，且每个坏字节从 1 字节涨成 3 字节** —— 这就是当年
「接口说 171196 字节、实际只有 94367 字节」的由来。

docx / xlsx / pptx / zip 同理：它们都是 zip 容器，
任一字节被替换都会让解包直接失败，所以 Office 一律报「已损坏」。

**已修复**：改为按字节读取，不做任何编解码；同时上传时显式带正确的
`Content-Type`（`docx` 不会再被当成裸二进制流）。

### 对前端的影响

| 项 | 说明 |
| --- | --- |
| **接口路径/方法/参数** | 无变化 |
| **响应体字段** | 无变化 |
| **`size` 字段语义** | ⚠️ **变了**：现在等于「文件真实字节数」，与用户下载到的文件大小一致<br>修复前是**损坏后的大小**（偏大）—— 所以旧记录里的 `size` 会比实际文件大 |
| **下载方式** | 无变化，仍是直连 OSS 的 `url` |

### 如果你想在下载卡片上显示大小

`artifact.size` 与 `file.fileSize` 现在都可信了，但**注意它已经是「数字」不是字符串**：

```js
// ✅ 对：Long 被全局序列化成字符串的是「雪花 ID」，size 是 Integer，仍是 number
const size = artifact.size ?? 0
const text = size > 1024 * 1024
  ? `${(size / 1024 / 1024).toFixed(2)} MB`
  : `${Math.ceil(size / 1024)} KB`
```

⚠️ 别对 `size` 用 `Number()` 之外的任何转换，也别对它做精度处理 —— 它远小于
`Number.MAX_SAFE_INTEGER`，就是个普通整数。

### 顺带修的（前端无感）

- OSS 上传时补了 `Content-Type`，`docx` 不再被浏览器当裸流强制下载；
  中文文件名仍做 percent-encoding（老链接不带编码，但依然可用）。
- 沙盒支持自定义模板（`E2B_TEMPLATE_ID`），可预装python-docx / openpyxl / python-pptx / dotnet / 中文字体。
  **这不是前端的事**，只是 AI 生成文档会更稳、不会中途降级手拼 OpenXML。

## 2026-10-06：首字延迟治理（第二轮）—— 记忆窗口大幅收紧

### 为什么要改

线上反馈「首字 4 秒，长会话 21 秒」。排查下来**不是**本机 CPU 或数据库慢
（实测本地前置处理只有 ~100ms 量级），而是**每轮发给模型的历史太大**：

模型在吐第一个字之前，必须先把整个 prompt（历史 + 工具定义 + 系统提示词）
计算一遍（prefill）。历史越长，首字越慢 —— 而且是**越聊越慢**。

### 改了什么（三处，全在后端配置/默认值）

| 项 | 改前 | 改后 | 影响 |
| --- | --- | --- | --- |
| `nexus.agent.memory.max-tokens` | `100000` | `24000` | 每轮最多带 2.4 万 token 的历史（原 10 万） |
| 模型元数据默认 `contextWindow` | `256000` | `65536` | 未填元数据时不再假定超大窗口 |
| 模型元数据默认 `maxOutputTokens` | `32000` | `16384` | 不再把 3.2 万当 `max_tokens` 发给服务商 |
| `deepseek-flash` 的元数据 | `1000000` / `384000` | `65536` / `8192` | 填的是模型**真实**能力 |
| 生产日志级别 | `debug`（prod 未覆盖） | `info`（prod 显式覆盖） | 不再逐条打印 SQL |
| 读历史的条数 | 全量 | 最近 200 条 | 长会话不再拉全量再丢弃 |

### 对前端的影响

| 项 | 说明 |
| --- | --- |
| **接口路径/方法/参数** | 无变化 |
| **响应体字段** | 无变化 |
| **SSE 事件** | 无变化 |
| **模型编辑表单的 placeholder** | ⚠️ **要改**：上下文窗口 `256000` → `65536`；最大输出 `32000` → `16384`<br>（详见 `docs/模型能力配置（前端）.md`，已同步） |
| **长会话行为** | ⚠️ **变了**：超过窗口的更早历史不再进入本次请求，模型可能「不记得」很早以前说过的话 |

### 前端建议配合做的两件事

1. **把「新建会话」做得更显眼**。
   记忆窗口收紧后，一个会话聊太久会开始丢上下文。与其让用户在同一个会话里
   无限聊下去（然后抱怨模型忘事），不如引导他在切换话题时开新会话。

2. **首字之前给一个可信的等待反馈**。
   后端现在已经能给出相对稳定的首字时间，前端不必再用「假进度条」。
   首帧事件里已经有 `runId` / `sessionId`（见 P2-5），可以直接用它做占位。

### 后端新增的可观测日志（排查用，前端不需要处理）

```
CHAT_PREFLIGHT runId=... quota=3ms convert=1ms context=12ms build=8ms total=24ms
CHAT_CONTEXT   runId=... match+model=2ms mcp=0ms skills+aiServices=9ms total=11ms window=24000 ctx=65536 out=8192 tools=15
CHAT_MEMORY    runId=... msgs=18 load=6ms limit=200
CHAT_TTFB      runId=... ttfb=1820ms
```

- `CHAT_PREFLIGHT.total` = 本地前置耗时；`CHAT_TTFB − total` ≈ **模型侧**耗时。
  两者一减就知道慢在我们还是慢在供应商。
- `CHAT_MEMORY.msgs` 撞上 `limit`（默认 200）说明会话已经很长。
- `CHAT_CONTEXT.window` 就是本次最多会带多少 token 的历史 —— 首字慢先看它。
