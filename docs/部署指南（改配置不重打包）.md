# 部署指南（改配置不重新打包）

> 面向：已经用 `java -jar` 或 Docker 部署在服务器上，**想加/改模型配置却不想重新打包重新上传**。
>
> 结论先说：**两件事都不用重打包。** jar 模式挂一个外部 yml 即可；Docker 模式连镜像都不用重建。

---

## 一、先回答「为什么要重打包」

`nexus.agent.system-models`（系统内置模型）现在写在 `application-prod.yml` 里，
而这个文件**被打进了 jar 包**（`nexus-agent-web/src/main/resources/`）。

所以直接改仓库里的 yml → 必须重新 `mvn package` → 重新上传 jar → 重启。
**这不是设计缺陷，是 Spring Boot 的默认行为**：jar 包内的 `classpath:/application-prod.yml`
优先级低于外部文件，只是外部文件默认没被用上。

Spring Boot 提供了 `spring.config.additional-location` 专门解决这个场景 ——
**外部文件压在上面，不用重新打包。**

> ✅ 已实测验证（`ExternalConfigOverrideProbe` 测试，用 Spring Boot 真实 ConfigData 机制）：
> 外部 yml 里的 `id` / `modelName` / `apiKey` 都能压过 jar 内的同名值。

## 二、方案 A：jar 模式 + 外部配置（改动最小）

### 1. 建配置目录

```bash
# 假设 jar 放在 /opt/nexus-agent/
sudo mkdir -p /opt/nexus-agent/conf
sudo vi /opt/nexus-agent/conf/nexus-override.yml
```

### 2. 写你要改的配置

```yaml
# /opt/nexus-agent/conf/nexus-override.yml
nexus:
  agent:
    system-models:
      # ⚠️ 这是**整体替换**，不是合并 —— 见下面「重要」那节
      - id: deepseek
        name: DeepSeek
        baseUrl: https://api.deepseek.com
        apiKey: ${DEEPSEEK}          # 仍可用环境变量占位符
        models:
          - modelName: deepseek-chat
            name: DeepSeek-V3
            contextWindow: 131072
            maxOutputTokens: 8192
      - id: qwen
        name: 阿里云百炼
        baseUrl: https://dashscope.aliyuncs.com/compatible-mode/v1
        apiKey: ${ALI_AI_KEY}
        models:
          - modelName: qwen3-max
            name: 通义千问-Max
          - modelName: qwen-vl-max
            name: 通义千问-VL（支持看图）
            vision: true
```

> 💡 `id` / `name` 不写会自动等于 `modelName`，只有「两家供应商有同名模型」时才需要写 `id`。
> 详见 [`docs/模型能力配置（前端）.md`](./模型能力配置（前端）.md)。

### 3. 改启动命令，加一个参数

```bash
java -jar nexus-agent-web.jar \
  --spring.config.additional-location=file:/opt/nexus-agent/conf/nexus-override.yml
```

**systemd 用户**（`/etc/systemd/system/nexus-agent.service`）：

```ini
[Service]
EnvironmentFile=/opt/nexus-agent/.env
ExecStart=/usr/bin/java -jar /opt/nexus-agent/nexus-agent-web.jar \
  --spring.config.additional-location=file:/opt/nexus-agent/conf/nexus-override.yml
```

### 4. 以后加模型就只做两件事

```bash
sudo vi /opt/nexus-agent/conf/nexus-override.yml   # 1. 改配置
sudo systemctl restart nexus-agent                  # 2. 重启
```

**不用重新打包，不用重新上传。**

### ⚠️ 重要：`system-models` 是整体替换，不是合并

外部 yml 里的 `nexus.agent.system-models` 会**整个替换** jar 内那份列表。
你只写一个模型，jar 内配的其它模型就**全没了**。

**两种做法**：

| 做法 | 怎么做 | 适合 |
|---|---|---|
| **A. 外部文件写全量**（推荐） | 把所有要用的模型都列在外部 yml 里 | 想完全掌控模型列表 |
| **B. 删掉 jar 内那份** | 保持外部文件为唯一来源，jar 内那段删干净 | 避免"两份配置并存"搞不清谁生效 |

验证方法（启动后看日志）：

```bash
sudo journalctl -u nexus-agent -n 200 | grep "系统模型已就绪"
# 应该看到你外部文件里配的每一个模型，数量对得上就说明生效了
```

**如果日志里数量比你配的少**，说明外部文件没被读到，检查：
- 路径写错（Linux 上必须是**绝对路径**，且 Java 能看到，不是 Git Bash 那种 `/tmp` 映射）
- 用了 `file:` 前缀但路径不存在 → **启动直接失败**（这是好事，总比静默不生效强）；
  想让它缺失也能启动就写 `optional:file:...`
- 忘了加 `--spring.config.additional-location` 参数

## 三、方案 B：Docker 部署

### 3.1 要上传哪些东西

用 `docker-compose.server.yml`（**服务器上用这个**，别用根目录的 `docker-compose.yml` ——
后者会新建空 PG 并执行 `001_baseline.sql`，**会 DROP 全表**）。

**必须上传**：

```
nexus-agent/
├── Dockerfile                        # 应用镜像
├── docker-compose.server.yml         # ★ 服务器用这个
├── pom.xml                           # Maven 根 pom（构建必需）
├── nexus-agent-common/
├── nexus-agent-domain/
├── nexus-agent-mapper/
├── nexus-agent-service/
├── nexus-agent-web/
├── nexus_agent_box/                  # 沙盒服务
│   ├── Dockerfile
│   ├── pyproject.toml
│   ├── uv.lock
│   ├── main.py
│   └── app/
├── scripts/check-env.sh              # 环境变量自查（强烈建议）
└── .env                              # ★ 你自己填的，不要提交
```

**不要上传**：

| 不要传 | 原因 |
|---|---|
| `.git` / `target` / `.idea` | `.dockerignore` 已排除，白占带宽 |
| `nexus_agent_box/.venv` | 镜像里用 `uv sync --frozen` 重装，`.dockerignore` 已排除 |
| `nexus_agent_box/docker-compose.override.yml` | 会把宿主机源码挂进容器盖掉镜像 |
| `nexus-agent-web/src/main/resources/application-dev.yml` | 被 gitignore，且容器跑 prod |
| `docs/` | 镜像构建用不到（但 `docs/sql/*.sql` 你要手动在数据库上执行） |

**传输方式**（`scp` 排除大文件）：

```bash
# 从本地（Git Bash）打包，避开 target / .git / .venv
cd /d/dev_project/jcode
tar --exclude='.git' --exclude='target' --exclude='.idea' \
    --exclude='.venv' --exclude='__pycache__' \
    --exclude='docs' --exclude='开发日志.md' \
    -czf /tmp/nexus-agent.tar.gz nexus-agent

# 上传
scp /tmp/nexus-agent.tar.gz root@<服务器IP>:/opt/
scp /d/dev_project/jcode/nexus-agent/.env root@<服务器IP>:/opt/nexus-agent/
```

### 3.2 服务器上启动

```bash
cd /opt/nexus-agent

# 沙盒服务也要一份 .env（OSS 变量名和 Java 侧不同，见 .env.example 注释）
cp nexus_agent_box/.env.example nexus_agent_box/.env
vi nexus_agent_box/.env

# 填应用环境变量，然后自查
vi .env
bash scripts/check-env.sh          # 退出码 0 才能启动

# 启动
docker compose -f docker-compose.server.yml up -d --build

# 验证：两个都要 healthy
docker compose -f docker-compose.server.yml ps
docker compose -f docker-compose.server.yml logs -f app
```

**启动命令就这一条**：

```bash
docker compose -f docker-compose.server.yml up -d --build
```

服务器**不用装 JDK 21**：构建阶段镜像自带 Maven + JDK，运行阶段自带 JRE。

### 3.3 ⚠️ 改了配置后不需要 `--build`

这是 Docker 相对 jar 的最大优势：

```bash
# 只是改环境变量（加 API Key、改 CORS 白名单…）
vi .env
docker compose -f docker-compose.server.yml up -d     # ← 不加 --build，几秒生效

# 只是改模型配置 → 见方案 C
```

`--build` 只在**代码或 Dockerfile 变了**时才需要。

> 📌 因为 `environment:` 优先级高于 `env_file:`，compose 文件里**故意没写** `SERVICE_IP`
> 和 CORS —— 它们只由 `.env` 提供，否则会覆盖你填的值（表现为"明明填了 IP 却连不上"）。

## 四、方案 C：Docker + 外部配置（最灵活，推荐）

Docker 下改模型配置连镜像都不用重建。给 app 服务挂一个配置目录：

```yaml
# docker-compose.server.yml 的 app 服务下加：
    volumes:
      - ./conf:/app/conf:ro        # 只读挂载
    environment:
      SPRING_CONFIG_ADDITIONAL_LOCATION: "optional:file:/app/conf/nexus-override.yml"
```

然后 `mkdir conf && vi conf/nexus-override.yml`，改完只要：

```bash
docker compose -f docker-compose.server.yml restart app     # 十几秒生效
```

**完整改动**（`docker-compose.server.yml` 的 `app:` 服务）：

```yaml
  app:
    build:
      context: .
      dockerfile: Dockerfile
    container_name: nexus-agent-app
    depends_on:
      box:
        condition: service_healthy
    volumes:
      - ./conf:/app/conf:ro
    environment:
      BASE_URL: http://box:8000
      SPRING_PROFILES_ACTIVE: prod
      SPRING_CONFIG_ADDITIONAL_LOCATION: "optional:file:/app/conf/nexus-override.yml"
    env_file:
      - .env
    ports:
      - "8080:8080"
    restart: unless-stopped
```

> 用 `optional:` 前缀是**故意的**：文件不存在时不报错，容器照常起。
> 想让配置写错时**启动就失败**（更早暴露问题），就去掉 `optional:`。

## 五、三种方式对比

| | jar 模式 | Docker（方案 B） | Docker + 挂载配置（方案 C） |
|---|---|---|---|
| 改模型配置 | 改外部 yml + 重启 | 同左（要挂载） | 改 `conf/` + `restart app` |
| 改环境变量 | 改 `.env` + 重启 | `up -d` | `up -d` |
| 改 Java 代码 | **重新打包上传** | `up -d --build` | `up -d --build` |
| 服务器装 JDK | 要（21） | 不要 | 不要 |
| 生效速度 | 十几秒 | 十几秒 | 十几秒 |
| 隔离性 | 无 | 较好 | 较好 |

**给你的建议**：
- 只是想解决"改模型要重打包" → **方案 A** 最小改动，今天就能上
- 已经在用 Docker → 直接上**方案 C**，配置彻底脱离镜像
- 长期运维 → 方案 C，配置、日志、数据都留在宿主机，好排查

## 六、别忘了这两件事

1. **环境变量要填全**：`bash scripts/check-env.sh` 退出码必须是 0。
   prod yml 里所有 `${XXX}` 缺一个都是**启动失败**（不是警告）。
2. **数据库迁移**：`docs/sql/001…007` 要在数据库上**手动执行过**。
   特别提醒 `007`（配额周期列）—— 缺列时**应用能起来，但登录/注册直接 500**
   （实体字段是普通字段，MyBatis-Plus 自动生成的 SQL 会带上这两列，
   手写 SQL 的降级兜底覆盖不到）。

## 六之二、🔴 web 与 box **独立部署**时必看（2026-10-07 补）

仓库根目录的 `docker-compose.server.yml` 是「**一套起**」：web 与 box 在同一个 compose 网络里，
Java 侧用服务名访问 box（`BASE_URL: http://box:8000`）。

如果你是**分开部署**（web 一个 compose、box 另一个 compose，甚至两台机器），有三处不同：

| 项 | 一套起 | 独立部署 |
|---|---|---|
| box 端口 | `expose: 8000`（仅容器网络内） | `ports: "8000:8000"`（必须对外，配置在 `nexus_agent_box/docker-compose.yml`） |
| **Java 的 `BASE_URL`** | `http://box:8000`（compose 服务名） | 🔴 **必须改成 box 的实际地址**，如 `http://<box 的 IP>:8000` |
| 启动命令 | `docker compose -f docker-compose.server.yml up -d --build` | `cd nexus_agent_box && docker compose -f docker-compose.yml up -d --build` |

🔴 **`BASE_URL` 是最容易漏的一处**：独立部署后如果沿用 `http://box:8000`，
所有沙盒工具都会失败（那个名字只在 compose 网络内解析）。
它是 **web（Java）侧的环境变量**，不是 box 侧的 —— 症状是"对话能发，但一用工具就失败"。

**box 侧代码更新（本次产物修复）**：

```bash
cd nexus_agent_box
docker compose -f docker-compose.yml up -d --build      # 注意带 -f，别合并 override
```

⚠️ 不带 `-f` 会自动合并 `docker-compose.override.yml`，把宿主机源码挂进容器 ——
"跑的代码 ≠ 镜像里的代码"，很容易误判成"配置生效了"，排查时极难察觉。

## 七、🔴 三个密钥：填错任何一个都是线上事故

> 这一节 2026-10-07 补。起因是「401 Invalid API Key 查不出原因」——
> **主密钥一旦漂移，用户所有已保存的 API Key 全部解不开**，
> 而后端只会看到厂商回的一句 401（真实原因被完全掩盖）。

| 环境变量 | 作用 | 填错的后果 |
|---|---|---|
| `API_KEY_SECRET` | **用户凭据的加密主密钥**（所有用户全部 LLM Key / MCP Token 的唯一根） | 🔴 见下方「必须固定」 |
| `JWT_SECRET` | JWT 签名密钥 | 不配会**随机生成** → **每次重启所有人被踢下线**（日志有 WARN） |
| `TAVILY_API_KEY` | 联网搜索（`web_search` 工具） | 不配只是**没有联网搜索**，不影响其他功能 |

### 🔴 `API_KEY_SECRET` 必须「一次生成、永久固定」

它决定所有用户凭据能否解开。**每次部署换一个值 = 所有用户的 API Key 全部报废**。

自检方法（部署后启动日志里会打一行）：

```
主密钥指纹=a1b2c3d4e5f6（长度 32，来源：环境变量 API_KEY_SECRET）
```

- **同一套环境的每次启动，指纹必须一致**。变了 → 存量密文全部解不开。
- 想换密钥，正确顺序是：① 保留旧密钥启动 → 导出并重新加密所有密文 → 再切新密钥。
  **直接改环境变量重启 = 数据报废。**

排查 401 时的正确顺序（别再怀疑 Key 本身）：

1. 看启动日志的**主密钥指纹**，与上次部署是否一致；
2. 看对话日志的 `CHAT_DECISION` 行：`模型=用户自带:xxx` 才是走加密链路；
   `模型=系统默认(...)` 说明用的是**系统内置模型的环境变量 Key**，与用户配置的 Key 无关；
3. 新版本（2026-10-07 起）解密异常会直接报中文错误
   「API Key 解密结果异常（含 N 个非可打印字符）」—— 看到这个就是主密钥漂移，
   不要再往 Key 有效性上想。

## 八、🔴 排查：配了 `TAVILY_API_KEY`，AI 却说「没有这个工具」（2026-10-08）

**先说结论**：这条 100% 是**环境变量没进到 Java 进程里**，不关代码的事。

`web_search` / `web_extract` 的设计是：**没读到 Key 就整个工具集不注册**
—— 模型压根看不见它，于是你问它，它只能说"没有这个工具"。
这是刻意的行为（"看得见却用不了"的工具对模型最糟，它会反复尝试白烧 token），
但代价就是：**配置没生效时，表面现象和"根本没做这个功能"一模一样。**

### 三步定位

**第 1 步：看启动日志里的「生效配置快照」。**
2026-10-08 起，启动时会打一张表，其中有这两行：

```
  联网搜索(web_search)     未启用（env TAVILY_API_KEY 未设置或为空）  ← <未配置>
  正文提取(web_extract)    未启用（env TAVILY_API_KEY 未设置或为空）  ← <未配置>
```

读到时会写成 `已启用（长度 32，形态正确）`。
**只报长度和形态，绝不打印 Key 本体**（日志会外发、会归档）。
形态那一项若提示"前缀不是 `tvly-`"，说明复制时缺了头或多了空格。

**第 2 步：确认进程真的带着这个变量。**

```bash
docker compose -f docker-compose.server.yml exec app env | grep TAVILY
# 看不到 → 变量没进容器；看得到 → 进去了，但进程是**在那之前**启动的
```

**第 3 步：让改动生效 —— 必须重建容器，不是 restart。**

```bash
# ✅ 正确：.env 改完，up -d 会检测到配置变化并重建容器
docker compose -f docker-compose.server.yml up -d

# ❌ 无效：restart 复用的是容器创建时的环境，改 .env 不影响它
docker compose -f docker-compose.server.yml restart app

# ❌ 无效：在容器里 export / docker exec 改 env，只影响那一条命令的子进程
docker compose -f docker-compose.server.yml exec app export TAVILY_API_KEY=...
```

> ⚠️ 根本原因：**Java 进程只在启动时读一次环境变量**。
> 所以「配了」和「进程读到了」是两件事，中间隔着一个"重启"。

### 顺带一提

`web_search` 与 `web_extract` **共用同一个 Key、同一个免费额度池**
（1000 credits/月是全部端点共享的，不是每个接口各 1000）。
两个工具要么同时可用，要么同时不可用 —— 只看到其中一个，说明还有别的问题。
